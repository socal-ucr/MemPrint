\title{Allocating What Programs Touch:\\
Non-Binding Per-Site Reservations from Measured Memory Footprints}
\author{Nafis Mustakin\\University of California, Riverside}
\date{October 2026}

\begin{document}

\begin{abstract}
A program asks the allocator for the memory it might need, and the operating system and a cluster scheduler
must honour every request, although the program often touches only part of it. We use \memprint{}, a Pin-based
footprint profiler, to measure what each allocation site requests and what the program touches in each block,
and we pass these measurements to the compiler and the runtime as \term{non-binding reservations}. The system has
three parts. First, a per-site mode of the Pin tool records each large block's touched bytes, highest touched
offset and touched page ranges, the calling context that allocated it, and the growth of every container; zeros
written over untouched memory do not count as use. Second, \pass{}, an LLVM 21 pass plugin, routes every allocation
through a runtime with a site identifier that survives edits elsewhere in the program, raises the capacity of
growing \texttt{std::vector}s, strings and hash tables per call site, with element sizes from the debug information,
and can embed the reservations in the binary. Third, \libmpr{}, linked or preloaded, commits only the predicted
prefix or ranges of a block and maps the rest \texttt{MAP\_NORESERVE}, so that an under-prediction costs commit
accounting and never correctness; it also skips the zeroing of pages a program has never touched. Every program
we ran produced its original output. On llama.cpp, which sizes and zeroes a KV cache for an 8192-token context,
\libmpr{} reduces peak commit by 86\% and peak RSS by 54\% with a 135M-parameter model (90\% and 45\% with a 360M
model), and profiles from other model sizes do as well. It reduces commit by 85\% on llama2.c, whose KV caches
are used in one range per layer, by 47\% on darknet AlexNet inference, and by 22\% on miniVite with the pass's
per-call-site container capacities. Across a 23-program HPC and interpreter corpus, where most programs already
hold about what they touch, it changes no output and no total RSS, keeps run time within $-5\%$ to $+7\%$, and
reduces total peak commit by 10.7\%. The pass adds 0 to 3\% to compile time, and 96.6\% of its site identifiers
survive an edit that changed 19\% of the previous ones. On 21 LLM inputs that no profile saw, the savings hold
with one profile per model, and a \term{periodic} reservation that combines the profile's layout with the run's
token count leaves no KV cache used beyond its commitment, where a reservation from the profile alone left up to
27\,MB. Finally, \memprint{}'s static interpreter now produces the same per-site profile from source: on GAP's
kernels it finds every site Pin finds, with total high water within 0.5\%, and its reservations perform as Pin's do.
\libmpr{} can also take the profile itself, from the pages each block touched, in one native run: over 28
configurations its reservations commit what the Pin profile's do (2{,}391 against 2{,}383\,MB) after 95\,s of
profiling instead of 21{,}676\,s. Mapping threads' stacks \texttt{MAP\_NORESERVE} cuts a further 60\% of the commit of
miniVite and llama.cpp, and a second run parameter, the prompt's length, leaves nothing beyond the commitment on 9
of 10 unseen llama.cpp inputs.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A program's memory request and its memory use are different quantities, and every layer below the program
plans for the request. The allocator maps what is requested, the kernel charges the mapping to the commit
limit~\cite{LinuxOvercommit}, and a batch scheduler on a cluster with disaggregated memory reserves the
request, or an estimate of it, before it places the job~\cite{Zacarias2021Accurate,Li2023Pond}. Our earlier
work built \memprint{}, a Pin-based profiler~\cite{Luk2005Pin,memprint} that measures the bytes a program
touches over its run, and showed that a scheduler which knows a job's footprint curve rather than its request
can pack jobs much more tightly~\cite{memprintsched}. However, a scheduler that reserves less than a program
requests does not change what the program asks for. The program still allocates the full request, and the
kernel still charges it.

The gap between request and use is large in some programs. darknet~\cite{darknet} running AlexNet inference
commits 534.7\,MB and touches 270\,MB, because it allocates training-only weight-update buffers that inference
never uses. llama.cpp~\cite{llamacpp} sizes its KV cache for the model's full 8192-token context and then writes
zeros over all of it, so a 32-token completion holds 189\,MB of cache in RAM and uses 0.4\% of it. miniVite's
edge list grows by doubling, so for a moment the old and new buffers are both live~\cite{minivite}.

Therefore, we ask whether a measured footprint can be passed down to the allocator, so that the program
obtains what it touches rather than what it requests, without trusting the measurement for correctness.
Specifically, we treat \memprint{}'s per-site measurements as \term{non-binding reservations}. A block always
receives every byte the program requested, but only the predicted part is committed, and the rest is mapped so
that the kernel backs it only if the program touches it. A wrong prediction then costs accounting and never
causes a fault the program can observe.
\emph{To the best of our knowledge, this is the first compiler pass and runtime that commit only the profiled
part of each heap block, leaving the rest to be backed on demand.} Existing profile-guided allocation work, such
as LLVM's MemProf, changes where an object is placed but commits every requested byte~\cite{MemProf}, and existing
container-sizing tools give advice to the programmer or replace data structures in managed
runtimes~\cite{LibstdcxxProfile,Makor2025Replacement} (\secref{sec:related}).

In this work, we make the following contributions:
\begin{itemize}
  \item We extend \memprint{}'s Pin tool to profile requested against touched bytes per allocation site, with
  each block's touched bytes, highest touched offset and touched pages measured exactly when the block is
  freed (\secref{sec:profile}).
  \item We extend the profile with calling contexts, so that a site reached through an allocation wrapper is
  split by its callers, with touched page ranges for blocks used sparsely across their length, with container
  growth chains, and with zeroing of untouched memory left out of use (\secref{sec:profile},
  \secref{sec:fit}).
  \item We present \pass{}, an LLVM pass plugin that gives every allocation call a site identifier that survives
  edits elsewhere in the program, routes address-taken allocators through thunks and large zeroing through the
  runtime, and raises the capacity of growing vectors, strings and hash tables per call site, with element sizes
  from the debug information (\secref{sec:pass}).
  \item We present \libmpr{}, a runtime that commits a block's predicted prefix or ranges and maps the rest
  \texttt{MAP\_NORESERVE}, matches reservations by calling context, grows blocks by moving page tables, skips the
  zeroing of pages that were never touched, and refuses address-keyed reservations profiled on another build
  (\secref{sec:runtime}).
  \item We fit reservations as functions of a run parameter when a block's use depends on the run rather than on
  its size: a \texttt{periodic} model takes the layout from the profile and the token count from the run
  (\secref{sec:fit}).
  \item We extend \memprint{}'s static interpreter to produce the per-site profile from source, keyed by the
  pass's identifiers through its site map (\secref{sec:static}).
  \item We evaluate the system on darknet, miniVite, two LLM inference engines and a 23-program corpus. It cuts
  llama.cpp's commit by 86\% and its resident memory by 54\%, and llama2.c's commit by 85\%, with identical
  outputs and no time cost, and we measure what each refinement adds (\secref{sec:eval}). The savings hold on
  21 unseen LLM inputs, and the parameterised reservation follows their lengths (\secref{sec:inputs}); the
  static profiles of GAP agree with Pin's site by site (\secref{sec:staticeval}).
  \item We report what the measurements show about footprint estimation: where miniVite's extra memory comes
  from, why the bytes a program touches can exceed its resident set, and why the time axis of a footprint
  curve matters more than its unit (\secref{sec:discussion}).
\end{itemize}

\section{Background}
\label{sec:background}

\subsection{Three measures of a program's memory}

We use three measures throughout, and the results depend on which one is meant.

\textbf{Bytes touched.} \memprint{}'s footprint is the number of distinct bytes the program has read or
written in memory that is still live, measured from every memory reference under Pin~\cite{memprint}. With
\texttt{-track\_frees}, a freed range leaves the footprint. Bytes touched are a property of the program and its
input, and they do not depend on the allocator or on the page size.

\textbf{Resident set (RSS).} The kernel counts the pages of a process that are in RAM. RSS includes file-backed
pages, such as a memory-mapped model file and the code of every shared library, and it counts a transparent
huge page as 2\,MB~\cite{LinuxTHP}. We sample it from \texttt{/proc/<pid>/smaps\_rollup} every 20\,ms and report
the peak sample. RSS is the quantity the kernel reclaims and the out-of-memory killer acts on, and it is the
"RSS truth" of the scheduling study~\cite{memprintsched}.

\textbf{Commit.} Linux charges private writable mappings to the commit limit when they are
created~\cite{LinuxOvercommit}. We measure commit as the total size of the mappings that
\texttt{/proc/<pid>/smaps} flags \texttt{ac} (accountable), sampled with RSS. A mapping created with
\texttt{MAP\_NORESERVE} is not charged. Under the default heuristic overcommit policy commit is only advisory,
but under strict overcommit (\texttt{vm.overcommit\_memory=2}) it is a hard limit, and in both cases it is the
memory the system has promised to the process.

\subsection{Why untouched memory is often free already}

Linux backs anonymous memory lazily. A large \texttt{malloc} or \texttt{calloc} block is served by \texttt{mmap},
and a page of it becomes resident only when the program first writes it, or reads it, in which case the kernel
maps a shared zero page that RSS does not count. Therefore, a block that the program never touches costs commit
but no RSS. darknet's 250\,MB of unused weight-update buffers are an example. Reducing RSS requires a change in
how memory is obtained, not a smaller reservation. In our measurements RSS fell only where the program, its
allocator, or the kernel touched pages the program did not need: vector growth that keeps two buffers live, a
zeroing \texttt{memset} over fresh memory, and transparent huge pages that back 2\,MB on the first touch.

\label{sec:related}

resizes heap allocations from a profile of what a program touches. To the best of our knowledge, no prior
compiler pass commits only the profiled part of a heap block and leaves the rest to be backed on demand.
The closest work falls into five groups, which \tabref{tab:related} summarises.

\textbf{Profile-guided compilation of allocation sites.} LLVM's MemProf is the closest existing compiler
work~\cite{MemProf}. It records, per allocation context (a call stack of function, line and column), the
allocation count, access counts at 64-byte granularity and lifetimes. Its \texttt{MemProfUse} pass matches the
profile to allocation calls through debug information, clones functions under LTO to separate contexts, and
rewrites \texttt{operator new} into a variant that carries a hot or cold hint, which an allocator such as TCMalloc
uses to place the object. \pass{} shares this structure: an instrumented profile, sites matched through the
inlined debug location chain, and allocation calls rewritten to a runtime that accepts site information.
However, MemProf changes only where an object is placed and leaves every requested byte committed, whereas
\pass{} and \libmpr{} change how much of each block is committed and how it is backed, and a site's reservation is a
size model rather than a temperature. MemProf's profile is collected by a sanitizer-style runtime in the
program itself, while ours comes from \memprint{}'s Pin tool, which needs no recompilation for the profiling run
and measures bytes rather than 64-byte granules.

\textbf{Profile-guided container sizing and selection.} Perflint traces C++ standard library operations and
reports where a better use exists~\cite{Liu2009Perflint}, and libstdc++'s profile mode, its descendant, prints
advice such as a vector's suggested initial size or a vector that is never filled to its reserved
size~\cite{LibstdcxxProfile}. The advice is for the programmer to apply, and libstdc++ notes that it depends on the
profiled input. Chameleon selects Java collection implementations from runtime metrics~\cite{Shacham2009Chameleon},
Brainy selects C++ data structures with machine-learned cost models~\cite{Jung2011Brainy}, and Makor et al.\
automatically replace data structures at allocation sites in GraalVM Native Image with versions specialised to
their profiled use, which reduces memory by up to 13.85\% (2.94\% on average for microservices)~\cite{Makor2025Replacement}.
The closest to our vector capacity is an IBM patent by Odaira, in which a Java JIT records the highest index
accessed per allocation context and sets the initial array size from it when it inlines the allocation
site~\cite{Odaira2015ArraySize}. Our capacity reservation differs in that it can only raise the capacity a growing
vector would have chosen, so a wrong prediction cannot shrink a block below its request, and it applies to C++
compiled ahead of time, with the profile taken from an unmodified binary.

\textbf{Bloat detection and heap profiling.} Xu et al.\ find Java data structures whose cost exceeds their
benefit~\cite{Xu2010LowUtility}, and Xu and Rountev find containers that are overpopulated or
underused~\cite{Xu2010Containers}. Heap profilers that report lag, drag and void, the time a block is allocated
but not yet or no longer used~\cite{Rojemo1996Lag}, and DHAT, which reports per allocation stack how many bytes
were read and written and flags blocks that are not completely filled in~\cite{ValgrindDHAT}, also diagnose
over-allocation. All of them leave the fix to the programmer. \memprint{}'s \texttt{-sites} profile reports
similar quantities, but the system acts on them without a source change.

\textbf{Placement, compaction and huge pages.} Mesh compacts the heap of unmodified C and C++ programs by
merging pages whose live objects do not overlap~\cite{Powers2019Mesh}, Maas et al.\ predict object lifetimes from
allocation call stacks to place long-lived objects together~\cite{Maas2020Llama}, and HALO groups heap objects by
profiled access affinity after link time~\cite{Savage2020HALO}. These systems use per-site profiles to change
placement, whereas we use them to change commitment and backing. jemalloc and TCMalloc's hugepage-aware
Temeraire return freed memory to the kernel more eagerly than glibc~\cite{Evans2006jemalloc,Hunter2021Temeraire},
but they still commit every requested byte. Ingens and HawkEye showed that transparent huge pages inflate the
resident set of sparsely used memory, and they promote a region to a huge page only when enough of it is used
or deduplicate zero-filled huge pages in the kernel~\cite{Kwon2016Ingens,Panwar2019HawkEye}. \libmpr{}'s
huge-page policy addresses the same bloat from user space, for the specific pages whose zeroing it skipped.
Yang et al.\ measured the cost of zeroing new memory in managed runtimes and made zeroing cheaper with
non-temporal and concurrent zeroing~\cite{Yang2011Zeroing}. \libmpr{} instead avoids writing zeros to pages that
are already zero, which saves resident memory as well as time.

\textbf{Calling contexts, stale profiles and partial commitment.} Several ideas we build on come from profiling
and operating systems. Calling-context profiling attributes a measurement to the chain of calls that led to it,
recorded as a calling context tree~\cite{Ammons1997CCT} or encoded cheaply as a probabilistic calling context
value per thread~\cite{Bond2007PCC}, and MemProf disambiguates allocation contexts by cloning functions under
LTO~\cite{MemProf}. We split a site by its caller frames, taken with the call frame information at allocation time,
which is enough to separate the callers of an allocation wrapper. Sample-based profile-guided optimisation keys
its profile by the line offset from a function's first line so that a profile outlives edits elsewhere in a
file~\cite{Chen2016AutoFDO,ClangSampleProfile}, and stale profile matching recovers a profile for a changed
binary~\cite{Ayupov2024Stale}. We use the offset scheme for site identifiers, and GNU build identifiers~\cite{GNUld}
to refuse address-keyed reservations on another build. Windows lets a program reserve address space and commit
chosen pages of it later~\cite{MSVirtualAlloc}, and Linux's \texttt{MAP\_NORESERVE} leaves a mapping out of the commit
charge~\cite{LinuxOvercommit}. Our shaped reservations commit chosen ranges of a block from a profile, without a
change to the program.

\textbf{LLM serving and memory pools.} PagedAttention allocates an LLM server's KV cache in fixed-size blocks as
tokens arrive~\cite{Kwon2023vLLM}, which requires paged attention kernels and a memory manager in the serving
framework. vAttention keeps the KV cache contiguous in virtual memory and backs it with physical GPU memory on
demand through the CUDA virtual memory API, which removes the kernel changes but still requires changes to the
serving framework~\cite{Prabhu2025vAttention}. Our llama.cpp result obtains the same kind of on-demand backing on the
CPU for an unmodified engine: the cache keeps its full virtual size, and only the pages it writes are backed,
because \libmpr{} skips the zeroing that would otherwise touch the whole cache. At cluster scale, Pond predicts
how much of a virtual machine's memory will stay untouched and places that part on a CXL pool~\cite{Li2023Pond},
Zacarias et al.\ show that a 60\% overestimate of memory demand reduces the throughput of a disaggregated system
by about 25\%~\cite{Zacarias2021Accurate} and resize each job's allocation to its use every five
minutes~\cite{Zacarias2023Dynamic}, and KS+ predicts a workflow task's memory over time from earlier executions with
other inputs~\cite{KSplus2024}. All three change what a system holds for a job, not what the job commits or
touches; \secref{sec:baselines} compares them with this work. These works motivate knowing what a job touches, which our earlier study
measured for scheduling~\cite{memprintsched} and this work passes to the allocator.

\figref{fig:overview} shows the pipeline. First, the program runs once under \memprint{}'s Pin tool with
\texttt{-sites}, which writes one row per large block. Second, \texttt{sites.py} fits each site's reservation
from one or more such runs. Third, the reservations reach \libmpr{}. A program can use the system in two ways.
In the \term{preloaded} configuration, \libmpr{} is loaded with \texttt{LD\_PRELOAD} into an unmodified binary,
a site is the return address of the allocation call, and the reservations come from a file. In the
\term{pass} configuration, the program is built with \pass{}, a site is a hash the compiler computes, and the
reservations can be embedded in the binary. Only the pass configuration can change a vector's growth capacity,
because the capacity is computed inside inlined library code, before any allocation call.

\section{Per-site profiling in \memprint{}}
\label{sec:profile}

The \texttt{-sites} mode of the Pin tool runs with the exact splitter, \texttt{-track\_frees} and the
bytes-touched footprint, which keeps one bit per byte for every touched page. It records, for every large block,
what the program asked for and what it did with it, and it writes four files: \texttt{*\_blocks.csv} (one row per
block of at least 64\,KB), \texttt{*\_sites.csv} (totals per site), \texttt{*\_capacity.csv} (container growth,
\secref{sec:profile-capacity}) and \texttt{*\_images.csv} (the images that site keys name, with their paths).

\subsection{Sites and calling contexts}

The tool hooks the allocator's entry points (\texttt{malloc}, \texttt{calloc}, \texttt{realloc}, the aligned
variants and every \texttt{operator new}). For the outermost allocator call of a thread it records the call's
return address, written as the image name plus the address in the image file (for example
\texttt{llama-completion+0x92266f}), which stays the same across runs despite address-space layout
randomisation. Because \texttt{operator new} is hooked as an allocator, an allocation made by inlined
standard-library code resolves to the program's own code. In a program built with \pass{}, the tool also hooks
\texttt{\_\_mpr\_alloc} and the other runtime entry points, reads the site identifier from the argument the pass
added, and names the site \texttt{id:0x...}.

A site is a single call, and a call inside an allocation wrapper serves every caller of the wrapper. llama.cpp
allocates its KV cache, its compute buffers and its weights' scratch space through one function,
\texttt{ggml\_aligned\_malloc}, so all of them share one site, although the program uses them very differently.
Calling-context profiling distinguishes the callers of a function by the chain of calls that reached
it~\cite{Ammons1997CCT,Bond2007PCC}, and LLVM's MemProf records allocation contexts as call stacks for the same
reason~\cite{MemProf}. With \texttt{-site\_context}~$k$ (2 by default), the tool records, for every allocation of
at least 64\,KB, the $k$ return addresses above the allocation call. It takes them with \texttt{PIN\_Backtrace},
which unwinds through the call frame information, so the program needs no frame pointers, and \libmpr{} takes
the same frames with glibc's \texttt{backtrace()} at run time. The frames are written with the block as image
keys, \texttt{frame1|frame2}. Backtraces are taken only for large requests, so a program's many small
allocations add no unwinding cost.

\subsection{Block summaries}

When a release (a \texttt{free}, a \texttt{realloc} that moves, or an \texttt{munmap}) is applied, the tool is
about to clear the block's bits from the footprint. Just before it does, it reads the block's touched bytes, the
offset of its highest touched byte and its number of touched pages from the per-page bitmaps, and it writes the
block's touched pages as runs, \texttt{first:count} relative to the block's first page, merging the closest runs
when there are more than 64. Releases are queued in order with each thread's buffered references, so a summary
sees every reference the program made to the block before freeing it. Blocks still live at exit are summarised
at exit. \texttt{calloc}'s own zeroing of a reused heap chunk is measured by a probe queued at the
\texttt{calloc} exit and recorded separately as \texttt{alloc\_touched}.

\subsection{Zeroing that does not count as a touch}

A program that clears a buffer it has just allocated writes every byte of it, so a bytes-touched profile counts
the whole buffer as used. llama.cpp clears its 189\,MB KV cache this way and then writes a few rows of it, so the
first profile reserved all of it. Writing zeros over memory that the program has not yet touched does not change
what the memory holds, and libmpr skips such writes (\secref{sec:runtime-zero}). With \texttt{-skip\_zeroing}, on by
default with \texttt{-sites}, the tool leaves these writes out of the footprint. It hooks the entry of every
\texttt{memset} and \texttt{bzero} implementation in the C library (skipping the IFUNC resolvers that select
among them, which the loader calls once), libmpr's \texttt{memset} and the pass's \texttt{\_\_mpr\_zero}. At each
entry it queues, in order with the thread's buffered references, the range that the call clears: $[p, p+n)$ when
the value is zero and $n \geq 4$\,KB, and an empty range otherwise. Stores made by the code of those routines are
tagged when they are instrumented, and a tagged store into the current range counts as time but does not set the
footprint's bits. A later read or write by the program touches the bytes as usual. A byte that was already
touched stays touched, so the option changes only what zeroing of untouched memory contributes. Yang et al.\
measured that zeroing new memory costs managed runtimes 2.7 to 4.5\% of their time on average and made it
cheaper~\cite{Yang2011Zeroing}. Here the point is that zeroing of untouched memory is not use.

\subsection{Container growth chains}
\label{sec:profile-capacity}

In a program built with \pass{}, a container that grows calls \texttt{\_\_mpr\_capacity} before it allocates its
new buffer (\secref{sec:pass-capacity}). The tool hooks that call and \texttt{\_\_mpr\_growth}, and it attaches the
capacity key, the call site that grew the container, to the buffer that the next allocation returns. Buffers with
the same key form a growth chain when each new buffer is larger than the previous one and is allocated while the
previous one is still live, which is how \texttt{std::vector}, \texttt{std::string} and hash tables grow. For each
key, \texttt{*\_capacity.csv} records the number of chains, the number of chains whose final buffer stayed below
64\,KB and the largest of those, and, for the other chains, the final buffer's size and its highest touched
offset, which is the bytes the container used.

\subsection{Images and builds}

An image key is an address in one build of an image and names unrelated code in another build. The tool writes
the full path of every image it saw, and \texttt{sites.py} records each image's GNU build identifier, a hash that
the linker writes into a note section~\cite{GNUld}, with the reservations (\secref{sec:runtime-build}).

\textbf{Tests.} The suite checks exact values on programs written for the purpose: a dead block, a block touched
only in a prefix, a block touched only at its tail, a \texttt{calloc} on a reused chunk, a \texttt{realloc} growth
chain, a growing vector, an allocation wrapper called from two functions that use their blocks differently, and
a 1\,MB buffer cleared with \texttt{memset} and then written in its first 64\,KB (touched: 64\,KB).

\textbf{Two further options.} In the course of this work we also added \texttt{-clock seconds}, under which the
timeline's snapshots are taken every $N$ milliseconds of wall time and every row carries a \texttt{Seconds}
column, and \texttt{-footprint pages}, which counts the 4\,KB pages that hold a touched byte. We use both in
\secref{sec:clock}.

\section{Fitting reservations}
\label{sec:fit}

\texttt{sites.py} reads the blocks of one or more profiling runs, keeps the blocks of at least 64\,KB (the ones
\libmpr{} serves), and fits, per site, the bytes a block will need as a function of its requested size $n$.

\textbf{Prefix models.} \libmpr{} commits a block from its start, so a prefix prediction is safe for a block only
if it reaches the block's last touched byte, and the fit uses the highest touched offset. Four models are
considered:
\begin{itemize}
  \item \texttt{dead}: $0$, when no block of the site was touched;
  \item \texttt{const}: $a$, when the highest offset does not grow with the request;
  \item \texttt{ratio}: $a\,n$;
  \item \texttt{affine}: $a\,n + b$, the lowest line through two blocks that lies above the covered blocks.
\end{itemize}
A model \term{covers} a set of blocks if its prediction reaches each block's highest offset. Among the models
that cover blocks holding at least a quantile $q$ of the site's requested bytes ($q = 0.9$ by default), the fit
keeps the one that commits the least over the training blocks. A site is left out when its best model would
commit at least 95\% of what was requested.

\textbf{Shaped reservations.} A block that is used sparsely across its whole length defeats a prefix. llama2.c's
KV caches are laid out as [layer][position][dimension], and a run of 128 tokens writes the first rows of every
layer, so the highest touched offset lies at 93\% of the block while 12.5\% of it is used. The \texttt{runs}
model commits a set of ranges of the block, given as fractions of its size: the union of the training blocks'
touched page runs, with the closest ranges merged until at most 128 remain. Windows separates reserving address
space from committing it, so that a program can commit only the pages it will use in a reserved
region~\cite{MSVirtualAlloc}, and the \texttt{runs} model applies the same split, chosen from a profile. The fit
keeps \texttt{runs} when it commits less than 70\% of the best prefix model and saves at least 64\,KB.

\textbf{Run parameters.} A KV cache shows the limit of fitting against the request alone: its size is fixed by
the context length, and its use grows with the number of tokens the run processes, which no allocation reveals. A
\texttt{runs} reservation commits what the profiled runs touched, so a longer run uses memory beyond it
(\secref{sec:inputs}). The \texttt{periodic} model is a hybrid of the profile and the run's parameters. The
profile gives the shape: every block is $K$ equal periods (one tensor per layer), each touched in a prefix of
the same length. The run gives the size: the prefix is fitted as $a\,T + b$ bytes, where $T$ is a run parameter
recorded with each profile (\texttt{params.txt}, here \texttt{tokens}). \libmpr{} reads the run's value from
\texttt{MPR\_PARAMS=tokens=}$T$ at start-up and commits the first $a\,T + b$ bytes of each period. With three
values of $T$ or more, $a$ and $b$ come from a least-squares line shifted up to cover every profile; with fewer, the
line passes through the origin with the largest prefix per unit of $T$. For llama.cpp with SmolLM2-135M, four
profiles (36 to 516 tokens, two context lengths) give $K = 60$, $a = 384$ bytes per token (a row of 192
half-precision values) and $b = 2.5$\,KB. The fit prefers \texttt{periodic} whenever a site's blocks have its
shape, also when it commits more on the training blocks, because only it follows $T$ to longer runs. The value of
$T$ has to come from whoever starts the job; for llama.cpp it is the prompt's token count (from the model's
tokenizer) plus the tokens to generate, and for llama2.c the number of steps, which is an upper bound because
llama2.c stops at the end of a story. This answers, for the KV cache, the limitation that a range reservation
transfers only between blocks of the same layout and use (\secref{sec:limits}).

A block whose touched runs start at the same places in every profile but grow with a run parameter gets a
\texttt{ranges} model: the starts, as fractions of the block, and each run's length, from its start to the end of
the run that covers it, fitted as $a\,P + b$ in the same way. llama.cpp's compute buffer is such a block: its 12
runs start at fixed pages, and their lengths follow the prompt's length, at about 26\,KB per prompt token, not the
number of tokens generated. Several run parameters can be recorded with a profile (\texttt{tokens}, \texttt{prompt});
the fit tries each and keeps, per site, the one that commits least on the training blocks, which puts the KV cache
on \texttt{tokens} and the compute buffer on \texttt{prompt}. A run's parameter must be the tokens it actually
processed: a profile of a run that stopped at an end-of-text token before the requested length, recorded at the
requested length, pulled the KV cache's fitted slope from 384 to 175 bytes per token.

\textbf{Calling contexts.} When a site's blocks have caller frames, the fit groups them by their first caller
frame, then by their first two, and fits each group separately. It keeps the shallowest grouping whose total
commitment is lower than the merged fit's by at least 5\% of the site's requested bytes. The site then gets one
line per context, \texttt{site@frame1[@frame2] model a b}, and its merged line, if it saves anything, serves
contexts that the profile did not see.

\textbf{Container capacities.} For each capacity key with chains whose final buffer reached 64\,KB, the fit
writes \texttt{key cap A B}: $A$ is the $q$-quantile of the final buffers' used bytes, and $B$ is the largest final
size of the key's small chains (0 when there are none). \libmpr{} reserves $A$ bytes once a container asks for
more than $B$, so that the many small containers that a call site may grow keep their usual growth.

\textbf{Builds.} For every image that an address key names, the file gets a line \texttt{\# image name build-id
hex}, read from the image's ELF note.

A profile can come from the same input the program will run on (we call this \term{own profile}, which
measures the mechanism) or from other inputs of the same program (\term{held out}, which measures how a
reservation transfers). The quantile leaves some blocks uncovered by design, and \secref{sec:robust} shows that
under-predictions are safe.

\section{The \pass{} compiler pass}
\label{sec:pass}

\pass{} is a new-pass-manager plugin for LLVM 21~\cite{Lattner2004LLVM}, 574 lines of C++, loaded into clang with
\texttt{-fpass-plugin}. It registers the same module pass at two extension points of the optimisation pipeline:
an early instance at \texttt{PipelineStartEP}, before inlining, which handles growth points, and a late instance at
\texttt{OptimizerLastEP}, after inlining, which handles everything else. It has three modes: \texttt{profile} (the
default) routes allocations through the runtime, \texttt{apply} also embeds a reservation file, and \texttt{off}
does nothing. \tabref{tab:rules} lists what it rewrites.

\subsection{Allocation calls and address-taken allocators}

For every call or invoke whose callee is an allocation function, the late instance builds a call to the matching
runtime entry point with the original arguments, a site identifier and a kind, replaces every use of the old call,
takes over its name and erases it. \texttt{operator new} under an \texttt{invoke} becomes a plain call followed by a
branch to the invoke's normal destination, because the runtime reports failure the way \texttt{malloc} does, and
the landing pad loses that predecessor.

An allocation function can also reach the program as a value: stored in a variable, passed to a function, or
placed in a table of function pointers, as libraries that let the caller choose an allocator do. A call through
such a pointer is an indirect call, and it bypasses the rewriting. The pass replaces every use of an allocation
function that is not the callee of a call with a thunk, an internal function with the same type whose body calls
the runtime with a site identifier of its own, derived from the location of the use. The uses in a constant, such
as an initialiser, share one thunk per module. Allocations made inside shared libraries that the build does not
compile reach \libmpr{} through symbol interposition~\cite{OracleLinker}: \libmpr{} defines \texttt{malloc} and its
siblings, so every library's calls resolve to it, with a return-address site and calling contexts.

\subsection{Stable site identifiers}
\label{sec:ids}

A site identifier must name the same allocation in a profiling build and an apply build, distinguish
allocations that the optimiser has inlined into different callers, and survive edits elsewhere in the program.
\pass{} computes a 64-bit FNV-1a hash over the callee's name, the name of the function that contains the call
after inlining, and the call's debug location chain from the innermost location outward through every
\texttt{inlinedAt} entry. An allocation inside an inlined \texttt{std::allocator::allocate} therefore resolves to the
program line that grew the container. Each level of the chain is hashed as the file's base name, the function's
name, the line relative to the first line of the function, and the column. Sample-based profiles key their counts
the same way, by the offset from the function's first line, so that a profile survives edits outside the
function~\cite{Chen2016AutoFDO,ClangSampleProfile}. The base name keeps the identifier independent of the directory
the program is built in. Without debug information the hash falls back to the function's name and the call's
position in it, so the build needs \texttt{-g} (line tables are enough). Ayupov et al.\ match stale profiles to a
new binary by the structure of its code~\cite{Ayupov2024Stale}. We use the simpler line-offset scheme and detect
what does not match: \texttt{scripts/check\_reservations.py} lists the reservations whose identifiers a new build no
longer has, from the site map that the pass writes (\texttt{0x... kind file:line function < ...}).

\subsection{Container capacities}
\label{sec:pass-capacity}

A \texttt{std::vector} that grows by \texttt{push\_back} doubles its capacity, copies its elements, and frees the old
buffer, so for a moment it holds both. libstdc++ computes the new capacity in \texttt{\_M\_check\_len}, libc++ in
\texttt{\_\_recommend}, \texttt{std::string} in \texttt{\_M\_create} (which takes the capacity by reference), and a hash
table chooses its new bucket count before \texttt{\_M\_rehash}. After inlining these calls no longer exist, so the
early instance wraps them before inlining:
\begin{lstlisting}
%len = call i64 @_ZNKSt6vectorI...E12_M_check_lenEmPKc(ptr %this, i64 1, ptr @.str)
%cap = call i64 @__mpr_capacity(i64 %len, i64 0, i64 8, i64 <point>) ; replaces %len
\end{lstlisting}
\libmpr{} returns at least \texttt{len}, so the capacity only grows: a wrong prediction cannot shrink a container,
and an excess is backed lazily. Three refinements make the prediction precise.

\textbf{Element size.} \texttt{\_\_mpr\_capacity} receives a count of elements, and the profile measures bytes. The
pass reads the element size from the debug information: the function that contains the growth point is a member
of the container's class, whose first template type parameter is the element type, and its size follows from the
DWARF type entry through typedefs and qualifiers~\cite{DWARF5}. A hash table's buckets are pointers (8 bytes), and
when the debug information has no parameters the pass passes 1.

\textbf{One capacity per call site.} The growth point sits in a template instantiation, such as
\texttt{\_M\_realloc\_insert<long>}, which every vector of that type in the program shares. A single capacity for all
of them would give the final size of the largest vector to every small one. When the optimiser inlines the growth
path into the program's code, as clang at \texttt{-O2} did for most \texttt{std::vector} growth in our programs, the late instance
finds \texttt{\_\_mpr\_capacity} with an inlined location chain that ends at the program's call, and it replaces the
instantiation's identifier with the call site's. When the growth path stays a call, for example
\texttt{basic\_string::\_M\_mutate} or \texttt{\_Hashtable::\_M\_insert\_unique\_node}, the pass brackets every call from
the program's own code to a container member that may grow it (\texttt{push\_back}, \texttt{insert},
\texttt{append}, \texttt{operator[]} and the libraries' internal growth functions, recognised from the demangled
name) with \texttt{\_\_mpr\_growth(id)} before it and \texttt{\_\_mpr\_growth(0)} after it, on both edges of an
\texttt{invoke}. A function is the program's own when its debug information names a file outside the system's
C++ headers. \texttt{\_\_mpr\_capacity} then uses the per-thread call site that \texttt{\_\_mpr\_growth} set. This is a
calling context of depth one, maintained by the program as in probabilistic calling context~\cite{Bond2007PCC}.
The libstdc++ profile mode and Perflint report a vector's suggested initial size to the
programmer~\cite{LibstdcxxProfile,Liu2009Perflint}, and an IBM patent sets a Java array's initial size from the
highest index accessed per allocation context~\cite{Odaira2015ArraySize}. Our capacity is set automatically, per
call site, and only ever raised.

\textbf{Small containers.} A call site can grow many small containers and a few large ones. The \texttt{cap} model
reserves the final size only once a container asks for more than the largest size that the call site's small
containers reached in the profile.

\subsection{Zeroing}

The late instance replaces \texttt{memset(p, 0, n)}, \texttt{bzero} and the \texttt{llvm.memset} intrinsic with a zero
value by \texttt{\_\_mpr\_zero(p, n, site)} when $n$ is at least 4\,KB or not a constant. A call that the compiler
would have emitted as a \texttt{memset} library call already reaches \libmpr{}'s \texttt{memset}, but code built with
\texttt{\_FORTIFY\_SOURCE} calls \texttt{\_\_memset\_chk} instead~\cite{GlibcFortify}, and a static binary has no symbol
to interpose. Smaller constant clears stay as they are, because the compiler expands them into stores.

\subsection{Embedding reservations}

In apply mode the late instance reads the reservation file and adds it to the module as a constant string,
\texttt{\_\_mpr\_embedded\_reservations}. Every translation unit carries a copy, so the global has
\texttt{weak\_odr} linkage in a COMDAT group of the same name, and the linker keeps one. (\texttt{weak\_any}
kept 48 copies in darknet's shared library, and \texttt{linkonce\_odr} was discarded as unreferenced.) \libmpr{}
declares the symbol weak and reads it at start-up when \texttt{MPR\_RESERVATIONS} is not set, so an apply build
needs no environment.

\subsection{Toolchain notes}

clang parses \texttt{-mllvm} options before it loads a \texttt{-fpass-plugin}, so the plugin's options are not
yet registered when they are parsed. The pass therefore reads \texttt{MPR\_PASS\_MODE},
\texttt{MPR\_PASS\_RESERVATIONS} and \texttt{MPR\_PASS\_SITEMAP} from the environment, and the same settings remain
available as options under \texttt{opt}. Our clang installation carries a configuration file that puts a newer
GCC's headers first, so builds pass \texttt{--gcc-install-dir} for the system GCC 8, whose libstdc++ the programs run
with, and \texttt{--no-default-config} where that newer GCC's intrinsics headers break the build. A build script
(\texttt{scripts/resize\_build.sh}) builds the plugin and \libmpr{}, sets these variables, links with
\texttt{--build-id}, and runs the program's own build command. Five \texttt{opt}-plus-FileCheck tests check the
rewriting of allocation calls, growth points of the three container kinds, zeroing and thunks, and end-to-end
tests build programs with the pass, profile them and run them with their reservations.

\section{The \libmpr{} runtime}
\label{sec:runtime}

\libmpr{} is about 1{,}000 lines of C. It defines \texttt{malloc}, \texttt{calloc}, \texttt{realloc},
\texttt{reallocarray}, \texttt{free}, the aligned allocators, \texttt{malloc\_usable\_size}, the \texttt{operator new}
variants, \texttt{memset}, \texttt{\_\_memset\_chk} and \texttt{bzero}, so it serves both a preloaded binary and a binary
built with \pass{}. A block smaller than \texttt{MPR\_MIN} (64\,KB) or at a site without a reservation goes to glibc
through \texttt{\_\_libc\_malloc} and its siblings, unchanged.

\subsection{Finding a block's reservation}

A request names its site by return address (preloaded) or by identifier (pass). When the reservation file has
context lines for that site, \libmpr{} takes the frames above the call with glibc's \texttt{backtrace()}, finds the
call's own return address among them, and looks up the deepest context line that matches the next frames, then
shallower ones, then the site's own line. \texttt{backtrace()} loads \texttt{libgcc\_s} on its first use, which
allocates, so \libmpr{} calls it once at start-up and guards against reentry. Only sites with context lines pay for
a backtrace, and only for large requests.

\subsection{Serving a block}

For a large block at a reserved site, \libmpr{} creates one anonymous mapping of the full size with
\texttt{MAP\_NORESERVE} and maps the predicted part again with \texttt{MAP\_FIXED} and without
\texttt{MAP\_NORESERVE}, which makes it accountable: the first $p$ bytes for a prefix model, or each range of a
\texttt{runs} model. The program receives a pointer to all $n$ bytes. If it touches beyond the prediction, the
kernel backs the page as for any anonymous memory, with no signal the program could observe. A design that
protected the remainder with \texttt{PROT\_NONE} and grew the block on a fault would also break system calls,
because a \texttt{read()} into a protected page returns \texttt{EFAULT} instead of faulting. A \texttt{dead} site's block is
entirely \texttt{MAP\_NORESERVE}. A large \texttt{calloc} needs no \texttt{memset}, because fresh anonymous pages are zero.
Blocks live in an open-addressing table keyed by address and in a sorted array of start addresses, which finds
the block that holds an arbitrary address. \texttt{free} recognises a runtime block by its page alignment and a table
lookup, records its resident bytes with \texttt{mincore} for telemetry, and unmaps it. The tables are themselves
mapped \texttt{MAP\_NORESERVE}, so \libmpr{} commits nothing of its own.

\subsection{Growing and shrinking}

A runtime block grows without copying where possible. \libmpr{} first tries to map the new tail directly after
the block with \texttt{MAP\_FIXED\_NOREPLACE}. If the address is taken, it reserves a new range and moves the
block's two mappings into it with \texttt{mremap(MREMAP\_FIXED)}, which moves page tables instead of data.
Growth is geometric, at least 1.5$\times$, so a table grown one element at a time does not remap at every step,
and a shrink is kept in place unless it halves the block. We found two kernel behaviours on the way. The kernel
keeps a tail that was added in place and written separately as its own mapping, and \texttt{mremap} fails with
\texttt{EFAULT} on a range that spans several mappings. A failed \texttt{mremap(MREMAP\_FIXED)} has also already
unmapped its destination. Open MPI's start-up (in \texttt{libpciaccess}) grows a table one element at a time
past the size threshold and crashed on the first version. \libmpr{} now maps the destination again and copies
such a piece. A block committed in ranges consists of many mappings, so it grows by a new block and a copy.

\subsection{Container capacities}

\texttt{\_\_mpr\_capacity(len, size, elem, point)} looks up the reservation of the call site that
\texttt{\_\_mpr\_growth} set on the thread (\texttt{cap:0x<site>}), else of the growth point (\texttt{id:0x<point>}, which
for an inlined growth point is already the call site's). For a \texttt{cap A B} model it returns
$\max(\texttt{len}, \lceil A / \texttt{elem} \rceil)$ once $\texttt{len} \cdot \texttt{elem} > B$, and \texttt{len} otherwise.

\subsection{Skipping the zeroing of untouched pages}
\label{sec:runtime-zero}

Programs that clear a buffer they have just allocated make every page of it resident. When \texttt{memset},
\texttt{\_\_memset\_chk}, \texttt{bzero} or \texttt{\_\_mpr\_zero} clears at least 16\,KB inside a runtime block, wherever in the
block it starts, \libmpr{} reads the range's entries from \texttt{/proc/self/pagemap}~\cite{LinuxPagemap} and writes
zeros only to pages that need them:
\begin{itemize}
  \item a page that is neither present (bit 63) nor swapped (bit 62) has never been touched since the block
  was mapped, and it reads as zero, so it is skipped;
  \item a page that is present but not mapped exclusively (bit 56 clear) is the kernel's shared zero page,
  mapped by an earlier read, or a page shared with a forked child, so \libmpr{} reads it and skips it if it
  is all zeros, which is correct in both cases;
  \item every other page, and the partial pages at both ends, are written.
\end{itemize}
Other \texttt{memset} calls go to glibc's implementation, found with \texttt{dlsym(RTLD\_NEXT)} at start-up (a
byte loop that GCC must not turn back into a \texttt{memset} serves the calls made before that).

The first version checked only the present bit. llama.cpp clears its KV cache a second time after a warm-up
decode, and attention had read the whole cache by then, so every page mapped the zero page and looked present.
After the zero-page check, 123\,MB of the cache were still resident. The cause was transparent huge pages,
which this machine enables for all anonymous memory: the warm-up writes a few rows into each layer's K and V
tensors (about 3\,MB each), and each first write faults in a 2\,MB page~\cite{LinuxTHP}. \libmpr{} therefore
marks the pages whose zeroing it skipped \texttt{MADV\_NOHUGEPAGE}. Those are the pages it chose to leave
untouched, and a huge page would undo the choice. Pages the program has touched keep huge pages.
\texttt{MPR\_THP=0} and \texttt{MPR\_THP=1} disable huge pages for all runtime blocks or leave them as the system
sets them, and \texttt{MPR\_ZERO=0} turns the zero skipping off.

\subsection{Builds}
\label{sec:runtime-build}

When the reservation file records an image's build identifier, \libmpr{} reads the build identifier of the image
it has loaded from its \texttt{PT\_NOTE} segment, the first time it makes a key in that image. If the two differ,
or the loaded image has none, it ignores that image's address keys and says so once on standard error. The pass's
identifiers do not depend on the build and are not checked.

\subsection{Threads' stacks}
\label{sec:stacks}

glibc maps a thread's stack, 8\,MB by default, as one committed region when the thread is created, although a
thread touches only as deep as it calls. \libmpr{} wraps \texttt{pthread\_create}: a thread created without a stack
of its own gets one mapped \texttt{MAP\_NORESERVE}, below a guard page, with the caller's other attributes
(detach state, scheduling, affinity) copied, and \texttt{pthread\_join} unmaps it. A stack is a reservation like
a block's, of zero committed bytes, and its pages are backed as the thread touches them, so a deep recursion
still works. A detached thread's stack stays mapped until exit, because no join says when it is free.

\subsection{Profiling at native speed}
\label{sec:nprof}

The reservations need a profile of each large block's touched pages, which \libmpr{} can measure itself. With
\texttt{MPR\_PROFILE=}\textit{dir}, it serves every large block, keeps transparent huge pages off them, and when a
block is freed (or at exit) writes the block's site, its two caller frames, its size, touched pages, high water and
runs of touched pages, read with \texttt{mincore}, in the Pin tool's \texttt{-sites} format, and the loaded images
with their paths for the build identifiers. A block's pages are fresh when \libmpr{} serves it and \libmpr{} skips the
zeroing of untouched pages, so its resident pages are the pages the program touched; the profile is exact to the
page, which is what a reservation is made of, and it costs one run at native speed. \texttt{sites.py} reads it like a
Pin profile. It differs from Pin's in two ways: a block grown by \texttt{realloc} is one row at its final size,
where the Pin tool records every buffer of the chain, and small blocks and container growth chains are not
profiled.

\subsection{Telemetry and settings}

With \texttt{MPR\_REPORT}, \libmpr{} writes per site at exit the number of blocks, the bytes requested,
predicted (committed), resident at free, the blocks that used more than predicted, and the zeroing it skipped.
\texttt{\_\_mpr\_committed()} returns the predicted committed total for a scheduler to read.
\texttt{MPR\_SCALE} multiplies every prediction for robustness tests, and \texttt{MPR\_ALL} serves every large block,
reserved or not, to measure the mechanism alone. Two lock-related fixes were needed: \texttt{dladdr}, used to name
a return-address site, is called outside \libmpr{}'s lock, and the exit handler releases the lock before it
writes the report, because \texttt{fclose} frees its buffer through \texttt{free}.

\section{Per-site profiles from source}
\label{sec:static}

\memprint{} has a second route to a footprint, which does not run the program: an abstract interpreter over the
clang AST that executes the program's source with concrete sizes and vectorised loops, charges every reference
to the object it touches, and reports the bytes touched~\cite{memprintstatic}. Its result was a footprint for the whole
program, not per-site data, so the reservations above came from Pin. We extended the interpreter to produce the
same per-site profile as the Pin tool, in the same files, so that \texttt{sites.py}, \pass{} and \libmpr{} take it
unchanged.

\textbf{Sites and contexts.} The interpreter records, for each heap object it creates (a \texttt{malloc}-family
call or a \texttt{new} expression), the source location of the allocating expression and the locations of the
calls that entered the functions above it, innermost first. Each interpreter frame keeps the call expression that
entered it; constructor calls, including delegating constructors, enter frames without going through the
interpreter's call path, and had to push their construct expressions explicitly, or a \texttt{pvector}'s buffer
would have been attributed to the caller of the function that built the \texttt{pvector}.

\textbf{Vectors.} The interpreter models \texttt{std::vector} instead of running libstdc++, and places every
vector's elements in one arena object. Each buffer the model creates (construction, \texttt{push\_back},
\texttt{resize}, growth) is recorded with its arena range, the call that made it and the buffer it replaced, which
links the buffers of one vector into a growth chain, as the Pin tool does at run time.

\textbf{Measures.} From the references the interpreter charged to each byte, a block's touched bytes, high water,
touched pages and page runs follow as the Pin tool measures them. The module writes
\texttt{Static\_<name>\_blocks.csv} and \texttt{\_capacity.csv}.

\textbf{Keys.} A static site is a chain of source locations, and a reservation needs the key the running program
will present. With the site map of the build that will run, which lists each identifier's allocation call and
the locations it was inlined at (\secref{sec:ids}), each block gets the identifier whose location chain is the
longest prefix of the block's chain, among identifiers of the same allocation function (a \texttt{realloc} and a
\texttt{malloc} on the same line are different sites). Locations inside the C++ library's headers are skipped,
since the interpreter models those functions rather than running them, and a vector's buffer is matched to an
identifier whose chain passes through the library function that its operation calls (\texttt{push\_back} to
\texttt{\_M\_realloc\_insert}, \texttt{resize} to \texttt{\_M\_default\_append}). Container chains are keyed by the
growth context (\texttt{cap:}) or the inlined growth point (\texttt{id:}), as the Pin tool keys them. A static
calling context beyond what the identifier inlined is dropped, because \libmpr{} matches further frames as
return addresses, which a static profile does not know.

\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

All runs used a two-socket Intel Xeon E5-2620 v4 (16 cores, 32 threads) with 62\,GB of RAM, Linux 4.18 (RHEL 8)
with heuristic overcommit and transparent huge pages set to \texttt{always}, GCC 8.5 and clang 21. Each
configuration ran three times, and we report the mean of the peak RSS and the peak commit, sampled every 20\,ms
for the program and its children. Outputs were compared by hash: all printed lines except those that report a
time or a rate, the modularity line for miniVite, the predictions for darknet, and the generated text for the LLM
engines.

The workloads are:
\begin{itemize}
  \item darknet AlexNet inference on 4 images~\cite{darknet}, built with GCC (preloaded) and with \pass{};
  \item miniVite~\cite{minivite} with 32768 vertices and 4 OpenMP threads, built with GCC (preloaded) and with
  \pass{};
  \item llama.cpp b11500~\cite{llamacpp}, CPU only, 4 threads, greedy decoding of "Once upon a time" with
  SmolLM2-135M-Instruct (32 and 128 tokens) and SmolLM2-360M-Instruct (64 tokens), both quantised to
  Q8\_0~\cite{SmolLM2}, at the model's default 8192-token context, built with GCC (preloaded) and with clang and
  \pass{};
  \item llama2.c~\cite{llama2c}, greedy, 128 steps, with the stories15M, 42M and 110M models;
  \item the 23 programs of the scheduling corpus~\cite{memprintsched} at their largest inputs: PolyBench kernels,
  GAP, HPCCG, LULESH, miniFE, Kripke, Quicksilver, NPB, darknet, miniVite, the Lua, Perl and Python
  interpreters, SQLite and GCC's cc1.
\end{itemize}
Each input has an \term{own} profile and a \term{held-out} profile from the program's other inputs (for darknet,
the reference and Extraction networks; for miniVite, 8192 and 16384 vertices). The profiles use the Pin tool with
\texttt{-sites}, which includes calling contexts and \texttt{-skip\_zeroing}. We call the system as first built
(prefix models only, one site per call, the first zero-skipping runtime) the \term{first version}, and the system
with calling contexts, shaped reservations, zeroing left out of the profile, and per-call-site container
capacities the \term{refined} version.

\figref{fig:improvements} and \tabref{tab:improvements} compare the first and the refined version. The
refinements reduce llama.cpp's commit by a further 79\% (265.1 to 55.6\,MB) and llama2.c 110M's by 83\% (72.8 to
12.1\,MB). Three refinements combine on llama.cpp:
\begin{itemize}
  \item \textbf{Zeroing left out of the profile.} The first profile counted the start-up \texttt{memset} as touching
  the whole 189\,MB KV cache, so the cache was committed in full. With \texttt{-skip\_zeroing}, the profile sees the
  rows the model writes.
  \item \textbf{Calling contexts.} The KV cache, the compute buffer and several small buffers are allocated through
  one site in \texttt{ggml\_aligned\_malloc}. The fit splits that site by two caller frames, and each buffer gets
  its own model.
  \item \textbf{Shaped reservations.} The KV cache is 60 tensors (30 layers, K and V), each written in its first
  rows. Its \texttt{runs} reservation commits 1.0\,MB of the cache, against 189\,MB for any prefix, and the compute
  buffer's commits 0.4\,MB of 115\,MB.
\end{itemize}
On llama2.c, the shaped reservation alone does the work: each KV cache gets one committed range per layer.
RSS falls further too (llama2.c 110M: 486.8 to 452.5\,MB), because ranges committed as separate mappings no longer
form transparent huge pages across the untouched rows between them. On miniVite, the refined version matches the
first version's hand-made capacity, with capacities fitted automatically per call site
(\secref{sec:minivite}).

\subsection{darknet: dead training buffers}
\label{sec:darknet}

\figref{fig:sites} shows what the profile found. darknet's largest site allocates the
\texttt{weight\_updates} buffers of its connected layers (\texttt{connected\_\allowbreak layer.c:35}) and convolutional layers
(\texttt{convolutional\_\allowbreak layer.c:196}), which only training uses, so inference never touches them. With its own
profile, \libmpr{} maps them \texttt{MAP\_NORESERVE}, and peak commit falls from 534.7\,MB to 284.6\,MB, close to the
270\,MB the program touches. RSS does not change, because the untouched buffers were never resident. The
\pass{} apply build, with the reservations embedded and no environment, gives the same 284.6\,MB. A held-out
profile from the reference and Extraction networks saves only 15.6\,MB, because those networks have no fully
connected layers: the profile has no data about the connected layers' site, which holds 234\,MB of AlexNet's
untouched buffers, and only the convolutional layers' 15\,MB carry over. A profile helps the code paths it covers,
and no refinement changes that.

\subsection{miniVite: container capacities and where its memory goes}
\label{sec:minivite}

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{figures/minivite.pdf}
\caption{Left: miniVite's bytes touched, its RSS at peak RSS and its commit at peak commit under glibc, by
mapping (smaps, 32768 vertices, 4 threads). Right: RSS and commit over time of the \pass{} build without
reservations and with its own profile.}
\label{fig:minivite}
\end{figure}

miniVite touches 15.4\,MB at its peak but holds 28.7\,MB of RSS at its peak RSS and commits 44.0\,MB at its peak
commit (\figref{fig:minivite}, left). The breakdown, from \texttt{/proc/<pid>/smaps} at each peak, explains the
gap:
\begin{itemize}
  \item \textbf{Code, not data, is a third of the RSS.} 9.6\,MB is library and program code (Open MPI,
  libstdc++, libgomp), which \memprint{} does not count because it measures data references, not instruction
  fetches.
  \item \textbf{Vector growth.} \texttt{edgeList} (\texttt{graph.hpp:777}) grows by \texttt{emplace\_back}
  without \texttt{reserve}, and it is the only large heap site live at the peak. When it doubles, the old
  6.3\,MB buffer and the new 12.6\,MB buffer are both live (18.9\,MB requested, 12.8\,MB touched), and huge pages
  back the new buffer's 6.5 touched MB with about 8\,MB.
  \item \textbf{Small blocks pay glibc's per-chunk overhead.} 1.8 million blocks smaller than 64\,KB (hash table
  nodes of 24 to 47 bytes and small vectors) request 57\,MB over the run but occupy 81\,MB of glibc chunks
  (1.42$\times$), and the heap holds them in 10.4\,MB at the peak.
  \item \textbf{Untouched library memory.} Open MPI's start-up allocates 1.6\,MB that it never touches.
  \item \textbf{Commit is mostly thread stacks.} 32\,MB of the peak commit is four 8\,MB OpenMP thread stacks, of
  which 2\,MB is resident. A smaller \texttt{OMP\_STACKSIZE} would remove that commit, which no allocator change
  can.
\end{itemize}
Built with \pass{}, miniVite has 20 growth points, 23 of them inlined into call sites in its own code, and 44
calls to container members bracketed as growth contexts. The profile of the 32768-vertex input yields 12
capacities: \texttt{edgeList}'s final size (6.5\,MB, one allocation instead of eight totalling 25\,MB) and those of
11 vectors whose growth stays out of line, reached through growth contexts. Two call sites, a vector and a hash
table, each grow about half a million small containers and get no capacity, because their chains never reach
64\,KB. With its own profile, peak RSS falls from 30.3\,MB to 27.0\,MB (11\%) and
peak commit from 34.0\,MB to 26.5\,MB (22\%), with the same modularity and run time (1.79\,s against 1.80\,s). The
held-out profile from 8192 and 16384 vertices reserves the 16384-vertex final size, half of what the 32768-vertex
edge list needs, and saves less (28.6\,MB RSS, 32.2\,MB commit).

The first measurement of the refined pass ran 15\% slower with reservations. The cause was \libmpr{}'s capacity
lookup, which formatted a key, took a lock and searched the site list at every growth of every container, about a
million times in this run. A table by numeric identifier, filled when the reservations load and read without the
lock, removed the cost, and the build without reservations became 17\% faster as well (2.17 to 1.80\,s).

\label{sec:llm}

\textbf{llama.cpp.} With the 135M model, llama.cpp allocates three large buffers through
\texttt{ggml\_\allowbreak aligned\_\allowbreak malloc}: a 188.7\,MB KV cache for 8192 tokens, a 115\,MB compute buffer of which 0.3\,MB is
touched, and two 44\,MB scheduler arrays (\texttt{ggml\_backend\_sched\_new}) that are never touched. It clears the
whole KV cache with \texttt{memset} at start-up and again after its warm-up decode. Under glibc, the whole cache is
therefore resident although a 32-token completion uses 0.4\% of it. The model's weights are mapped from the GGUF
file, so their 143\,MB count in RSS but not in commit.

RSS and commit fall for different reasons (\figref{fig:llamacpp}). RSS falls from 380\,MB to 175\,MB because of
the zero skipping. To attribute it, we recorded each buffer's address and measured its resident pages at the
peak from \texttt{/proc/<pid>/pagemap} under four configurations of the first runtime. Without zero skipping,
the KV cache holds 188.7\,MB, as under glibc. Skipping the zeroing alone leaves 123.7\,MB, all of it huge pages
faulted in by the warm-up's writes of one row per layer. Skipping the zeroing and keeping huge pages off the
skipped pages leaves 1.0\,MB. The compute buffer holds 15 to 17\,MB under every configuration, which is the part
llama.cpp uses at the peak, and the remaining 174\,MB (weights, heap and code) does not change. Commit falls
from 404.5\,MB to 55.6\,MB because of the reservations (\secref{sec:refined}): the scheduler arrays are
\texttt{dead}, and the KV cache and the compute buffer are committed in ranges. Run time does not change (0.71\,s
against 0.73\,s for 32 tokens, 1.81\,s against 1.95\,s for the 360M model).

\label{sec:llama2c}
\textbf{llama2.c.} llama2.c's KV caches are also sized for the full sequence (37.7\,MB each for the 110M model,
of which 4.7\,MB is touched for 128 of 1024 positions). It allocates them with \texttt{calloc} and does not clear
them, so their untouched part was never resident under glibc either. They are laid out as
[layer][position][dimension], so every layer's first rows are touched and the highest touched offset lies at 93\%
of the block (\figref{fig:sites}). A prefix reservation must cover it: the first version committed 72.8 of
78.2\,MB. The shaped reservation commits one range per layer, 12.1\,MB in all. The held-out profile, from models
with 6 and 8 layers, places its ranges where a 12-layer model's are only in part, and commits 45.8\,MB.

A profile describes the input it was taken on. We ran both engines on 21 inputs that no profile saw, with the
reservations from each model's default-input profile (\tabref{tab:inputs}). All 189 runs produced glibc's output.
llama.cpp's commit stays at about 56\,MB on every input, 78 to 90\% below glibc's, and its RSS falls by 24 to 53\%.
llama2.c's falls by about 80\% for the 42M and 110M models. Profiling the new input itself gains nothing: for
llama.cpp at 512 tokens the input's own profile commits 54.9\,MB (56.0 per-model), at context 2048 56.2\,MB (55.7),
and for llama2.c 42M at 512 steps 10.0\,MB (7.7), because its ranges cover the rows the longer run writes.
Pooling the profiles of all models of an engine costs little for llama.cpp (56.3 to 57.8\,MB) and much for
llama2.c (49\,MB instead of 13\,MB for 110M), whose models have 6, 8 and 12 layers, so the ranges of one fall
elsewhere in another's blocks.

The commit, however, stops describing the run when the run is longer than the profile. The per-model reservation
of llama.cpp's KV cache covers the rows of a 36-token run, so a 1{,}024-token run writes 23.4\,MB beyond it, and
llama2.c 110M writes 27.2\,MB beyond it at 1{,}024 steps (\figref{fig:inputs}). This is safe, since the kernel
backs those pages on touch, but a scheduler reading the commit would under-count the job. The \texttt{periodic}
reservation (\secref{sec:fit}) removes it. With $T$ from the run, no KV cache was used beyond its commitment on
any input, except 0.25\,MB on the 136-token prompt, and the commit grows with the run: 56.7\,MB at 20 tokens, 62.1
at 260, 68.0 at 516 and 80.0 at 1{,}032 for llama.cpp 135M, against 405\,MB under glibc. RSS does not change, since
the same pages are touched either way. The four profiles are not needed: fitted from the 32-token profile
alone (through the origin, 455 instead of 384 bytes per token), the reservation commits 56.2 to 83.8\,MB on the
same inputs, 3.7\,MB more than the four-profile fit at 1{,}032 tokens, and again no KV cache was used beyond its
commitment, with identical outputs. For llama2.c the parameter is the number of steps, which bounds the tokens
from above, because a story usually ends after about 200 tokens. A 1{,}024-step run therefore commits the whole
cache (78.9\,MB for 110M, glibc's 78.2\,MB plus the page rounding of 12 periods), where the per-model reservation
commits 12.5\,MB and the run uses 27.2\,MB beyond it; at 256 steps the periodic reservation commits 22.5\,MB and
covers the run exactly.

What remained beyond the commitment was outside the KV cache: 1.35\,MB at a small site whose \texttt{const}
reservation came from one profile, and llama.cpp's compute buffer, whose used ranges grow with the number of
prompt tokens processed in one batch, not with the run's length (4.3\,MB beyond its ranges with the 136-token
prompt, 11.7\,MB for the 360M model). The profiles had prompts of 4 to 8 tokens, so the fit had nothing to relate
it to.

water was the larger one in every case, because it follows both sides of data-dependent branches, which errs in the
safe direction for a reservation.

Only one site in these kernels requests much more than it uses: sssp's frontier, a \texttt{pvector} sized to the number of edges
(\texttt{sssp.cc:92}), a block of 7.3 to 30.4\,MB per trial of which 11 to 32\,KB is
touched. Fitted from three scales, the interpreter's profiles give it $0.000987\,n + 2.1$\,KB and Pin's
$0.00103\,n + 1.1$\,KB, and both commit 12 to 32\,KB of each frontier with no block used beyond its commitment.
Fitted from scale 16 alone, both routes give a constant that larger scales outgrow by 7 to 20\,KB per block. We ran all 12 kernel and scale pairs
with the corpus's arguments (4 or 8 trials), without reservations and with the reservations of each route (3 runs
each): every run produced the same output, peak RSS and commit were the same with either route's reservations,
and time stayed within 0.99 to 1.04 of the build without reservations. The frontier is not live at the peak, which
comes while the graph is built, so it lowers the commit while sssp runs but not its peak (except at scale 16, 32.5
to 31.7\,MB).

\textbf{Cost.} We timed both profilers again, one process at a time on the idle machine (\tabref{tab:static}). Pin's
exact \texttt{-sites} profile ran 65 to 97 times slower than the program (15 to 82\,s) and held 0.46 to 1.5\,GB.
The interpreter ran 86 to 1{,}344 times slower (19\,s to 20\,min) and held 1.4 to 11.4\,GB, so it took 1.3 to 14.8
times as long as Pin and 3 to 7 times its memory; over all twelve profiles, 2{,}751\,s against 472\,s. The ratio
depends on the kernel more than on the scale: cc 1.3 to 1.4, bfs 1.9 to 2.1, sssp 3.0 to 3.3 and pr 13 to 15. Both slowdowns fall slightly with scale, the
interpreter's from 1{,}344 to 1{,}234 on pr and 286 to 223 on sssp, and its memory grows with the input, about in
proportion to the program's (1.4\,GB at scale 16 to 5.1\,GB at 18 for pr, 3.2 to 11.4\,GB for sssp). So it
is not a cheaper way to profile a program that Pin can run. What it shows is that the per-site profile, and the
reservations, can come from the source alone, with no instrumented run, and agree with the measured ones on the
code it can execute. Its limit is the programs it can run: GAP's and the regular C/C++ codes of our earlier study~\cite{memprintstatic}, not miniVite
(MPI), darknet or the LLM engines, which read their sizes from model files.

\subsection{Robustness to wrong predictions}
\label{sec:robust}

Under-prediction is safe by construction, and we tested it. With every prediction multiplied by 0.1
(\texttt{MPR\_SCALE=0.1}), darknet and miniVite produced identical outputs, and the telemetry reported the
blocks that used more than predicted. The quantile in the fit leaves blocks uncovered by design, and held-out
profiles under-predict on the LLM engines and the corpus, again with identical outputs. Over-prediction costs
commit and nothing else, because the committed part is still backed lazily. A container capacity can only raise
the capacity a container would have chosen. Two control programs with no waste, PolyBench 2mm and HPCCG, with
\libmpr{} serving every large block (\texttt{MPR\_ALL}), changed by at most 1.8\,MB of RSS and 0.1\,MB of commit.

\centering\small
\resizebox{\linewidth}{!}{\input{tables/baselines_strict.tex}}

\label{tab:baselines-workloads}
\end{table}

Three published systems reduce the memory a job is given: Pond~\cite{Li2023Pond} places the part of a virtual
machine's memory it predicts will stay untouched in a CXL pool, the dynamic provisioning of Zacarias et
al.~\cite{Zacarias2023Dynamic} resizes a job's allocation to its use every five minutes, and KS+~\cite{KSplus2024}
reserves a step function over time that it learns from earlier executions with other inputs. They act on what a
system holds for the job; \pass{} and \libmpr{} act on what the job commits and touches. We compare them on the
recorded runs of this section (\texttt{paper\_resize/baselines.py}), with the policies of our scheduling
study~\cite{memprintsched}, where all three are implemented as scheduler oracles and checked against the authors'
code where it is published. Every approach starts from an exact request, the job's peak of commit and RSS under
glibc, so none gains from a user's overestimate. Pond holds the request and keeps in local DRAM only the request minus
its predicted untouched memory, taken from the job's other runs of the same input (its per-customer history at its
best). Dynamic provisioning holds the request for the first sixth of the run (five minutes of a median 30) and then
each sixth's largest use, read from the run itself, as their simulator reads it from the usage trace. KS+ predicts
from the RSS of the program's other corpus inputs and re-runs the job with its retry strategy when the use exceeds
the reservation; we report it with the authors' 100\,MB floor on every predicted peak and with a 1\,MB floor,
since the 100\,MB floor exceeds the whole footprint of many of our programs. \pass{} is given the same exact request
under \libmpr{}: the peak of commit and RSS of the run with its reservations.

\tabref{tab:baselines} gives the totals and \tabref{tab:baselines-workloads} the workloads. \libmpr{} with its own profile holds 3{,}765\,MB on time average against
4{,}905\,MB for the request, 23\% less, and 18\% less with a held-out profile, under either demand. Dynamic
provisioning holds 10\% less than the request when the demand is the RSS and 4\% less when it includes the commit,
which it cannot change; with a resize every sixtieth of the run it holds 3{,}763\,MB under the RSS demand, as much as
\libmpr{}, but only because each resize is the coming interval's largest use, which a running system cannot know.
Pond holds the whole request, as it never fails, and keeps 6\% of it out of local DRAM, almost all of it darknet's
dead training buffers (247 of 299\,MB), which \libmpr{} does not commit at all. KS+ holds more than the request: its
extrapolation from the two smaller inputs reserves 8.5 times GCC's cc1 peak (1{,}140 against 134\,MB), and with the
authors' floor every small program holds at least 100\,MB. Without cc1 and with a 1\,MB floor it holds 2\% less
than the request, with 36 failures over all runs.

The gain of \libmpr{} that none of the three can obtain is on the LLM engines. Under glibc, llama.cpp touches its
whole KV cache when it clears it, so its RSS is its commit, and no system can give it less without killing it; with
\libmpr{}, the clearing skips untouched pages, and the RSS itself falls from 380 to 177\,MB (135M model) and from 767
to 419\,MB (360M model). The approaches compose: dynamic provisioning applied to the runs under \libmpr{} holds
3{,}553\,MB, 28\% less than the request, and Pond's local DRAM under \libmpr{} is 3{,}763\,MB, because \libmpr{}
has already removed most of the untouched memory Pond would place in the pool.

In the scheduling study, a \memprint{} curve needed about 60\% headroom to cover the RSS truth, and we attributed
part of that to the time axis, since \memprint{} counts memory references while RSS is sampled in
seconds~\cite{memprintsched}. The new options let us test the attribution. We reran the full trace and the 5\%
windowed mode at every program's largest input with \texttt{-footprint pages}, and mapped each curve to the wall
time recorded in the \texttt{Seconds} column (\tabref{tab:clock}, \figref{fig:margins}). On wall time, the full
trace's 90th-percentile margin falls from 0.58 to 0.44, and the mean response time from 1{,}847 to 1{,}476
minutes. The programs that gain most have phases that are short in references but long in time, such as GAP BFS
(margin 0.53 to 0.06), GAP CC (0.56 to 0.09) and Lua (0.70 to 0.05). Counting pages instead of bytes helps the
programs whose touched bytes are scattered (cc1 0.25 to 0.13, Perl 0.29 to 0.13, miniVite 1.12 to 0.84), but it
does not reduce the calibrated margin on its own. Together the two options give 0.41 and 1{,}423 minutes, still far
from the exact peak's 436 minutes. The remaining margin comes from memory that \memprint{} does not count, such
as miniVite's library code, which the scheduler's RSS baseline (the run's smallest sample, taken before MPI
loads its libraries) treats as footprint. The wall time is measured under Pin, which slows phases unevenly, so
it approximates native time.

\subsection{Bytes touched can exceed the resident set}

With the first profile, llama.cpp's RSS under \libmpr{} (193\,MB) fell below its bytes touched as \memprint{}
measured them (353\,MB at the peak, with the mapped weights). The difference was the zeroing \texttt{memset}:
writing zeros to fresh anonymous memory counts as touching it, although no reader can distinguish the result from
untouched memory. \texttt{-skip\_zeroing} now leaves such writes out of the profile (\secref{sec:profile}), which is
what let \libmpr{} commit 1\,MB of the KV cache instead of 189\,MB. It is on with \texttt{-sites} only: the footprint
truth of the scheduling study keeps its definition, in which a write is a touch whatever it writes. Whether the
truth should also leave out zeroing of untouched memory is a question of definition. Under it, the truth would
follow the resident set of a program run with \libmpr{} more closely, and the resident set of a program run
without it less closely.

\subsection{What the RSS numbers measure}

The RSS figures in this paper are peaks of samples of \texttt{smaps\_rollup}, taken every 20\,ms, so a spike
shorter than the interval can be missed. They include file-backed pages and count a huge page as 2\,MB. The
per-buffer figures for llama.cpp come from a different instrument. A logging library recorded where glibc (or
\libmpr{}) placed each buffer of at least 1\,MB, without changing how it allocated, and at the sample with the
largest total RSS we counted each buffer's pages that pagemap reports as present and mapped exclusively, which
excludes the shared zero page. Under glibc the KV cache and the compute buffer lie in one merged mapping, so
\texttt{smaps} alone cannot separate them.

\subsection{Where resizing pays}

The results separate three cases. A program that allocates buffers it never touches (darknet, llama.cpp's
scheduler arrays) gains commit but no RSS, because the kernel never backed those buffers. A program whose
allocator or own code touches memory it does not need (a zeroing \texttt{memset}, vector doubling, huge pages over
sparse writes) gains RSS, and only a change in how the memory is obtained recovers it. A program that already
uses what it allocates, which is the median program in our corpus, gains nothing and loses nothing.

\section{Limitations and future work}
\label{sec:limits}

A limitation of the container capacities is that a capacity measured on one input transfers to another only as
far as the final sizes agree. The final size of miniVite's edge list depends on the graph, so a capacity from the
8192- and 16384-vertex inputs reserves the 16384-vertex size, half of what the 32768-vertex input needs, and the
vector still grows once more (\secref{sec:minivite}). Predicting the final size from the input would need a model
of size against the input's parameters, as the \texttt{periodic} model does for KV caches, or a per-site profile
from source (\secref{sec:static}), which the interpreter cannot produce for miniVite, an MPI program. The growth points are specific to the containers of libstdc++ and
libc++ listed in \tabref{tab:rules}; \texttt{std::deque} grows in fixed 512-byte nodes and has no capacity to raise.

A limitation of the shaped reservations is that a range is a fraction of the block, so it transfers between
blocks of the same layout and use. llama2.c's held-out reservations, from models with 6 and 8 layers, cover a
12-layer model's KV caches only partly, and commit 46\,MB against 12\,MB with the model's own profile. The
\texttt{periodic} model names the layout and follows the run's length (\secref{sec:inputs}), but its number of
periods and bytes per token are a model's, so it is fitted per model, and its parameter has to be supplied by
whoever starts the job; without it, \libmpr{} assumes the largest value profiled. A parameter is only as good as
its relation to the use: llama2.c's steps bound its tokens from above, so a run that ends early is over-committed.
The \texttt{ranges} model's starts are fractions of the block, so they hold for one layout: llama.cpp's compute
buffer at another context length is laid out differently (\secref{sec:inputs}).

Calling contexts are taken with a backtrace for each large allocation at a site that has context lines. The
frames are return addresses, so they are tied to a build, as image keys are, and a context deeper than two frames
is not tried.

Small blocks are left to glibc, so the per-chunk overhead of small allocations, 1.42$\times$ in miniVite, is not
addressed. Allocators inside interpreters (pymalloc, Lua's tables) and custom \texttt{operator new} are not
covered beyond the large blocks they request from the system.

The commit saving depends on the overcommit policy. Under strict overcommit (\texttt{vm.overcommit\_memory=2}) the
kernel ignores \texttt{MAP\_NORESERVE}, so the saving disappears, although correctness is unaffected; we could not
set the policy on our machine to measure it. The zero skipping reads pagemap, which unprivileged processes may read
on this kernel without page frame numbers, and its zero-page check treats a page shared after \texttt{fork}
conservatively by reading it; no workload we ran forks. Keeping huge pages off the skipped pages cost no time on
llama.cpp, but a program that clears a buffer and then fills all of it densely would run on 4\,KB pages there.

Profiling under Pin is expensive: the Pin tool's exact mode with \texttt{-sites} took 300 to 1{,}100\,s for llama.cpp
runs of 0.8 to 2\,s, and 617\,s for llama2.c 110M (18\,s natively). \libmpr{}'s own profile removes that cost for
the large blocks a reservation needs, at the price of whole pages and final sizes (\secref{sec:nprof}); the Pin tool
is still needed for container growth chains, small blocks and byte-exact footprints. The interpreter avoids the
instrumented run but was slower than Pin on GAP, 1.3 to 14.8 times its time and 3 to 7 times its memory
(\secref{sec:staticeval}, \secref{sec:cost}). We ran single short completions; an LLM server that
runs many sequences fills its KV cache over time, and its savings would shrink as it does.

\section{Conclusion}
\label{sec:conclusion}

We passed \memprint{}'s measured per-site footprints to a compiler pass and a runtime as non-binding
reservations, so that a program is backed by what it touches rather than what it requests, and an
under-prediction costs accounting instead of correctness. Every program we ran produced its original output.
Calling contexts, shaped reservations and a profile that does not count zeroing as use took the system from a
34\% to an 86\% commit reduction on llama.cpp and from 7\% to 85\% on llama2.c, and zero skipping halves
llama.cpp's resident memory. Per-call-site container capacities, with element sizes from the debug information,
remove miniVite's vector growth without slowing it, once the runtime's lookup is fast enough for a million
growths. The 23-program corpus, which already holds about what it touches, saw no regressions. The measurements
also showed that a footprint curve is most useful to a scheduler on a wall-clock axis, and that what a profile
counts as use, such as zeros written to fresh memory, decides what can be saved. A profile describes its input:
on unseen LLM inputs the savings held, and a reservation that takes the KV cache's layout from the profile and its
length from the run kept the commitment in step with the use. The per-site profile can also come from source:
\memprint{}'s interpreter reproduces Pin's profiles of GAP site by site, so the static route can now feed the
same reservations, for the programs it can run.

The runtime can do more of the work itself. Taking the profile from the pages each block touched, in one native run,
gave the same reservations as the Pin profile at a two-hundredth of its cost; mapping threads' stacks
\texttt{MAP\_NORESERVE} removed most of the commit that remained in the multithreaded programs; and a second run
parameter, the prompt's length, let the reservations follow llama.cpp's compute buffer as the first follows its KV
cache.
