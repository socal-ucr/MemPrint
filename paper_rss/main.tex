\title{Memory Footprints from Resident Memory and Allocator Statistics:\\
A Footprint Model at the Cost of a Native Run}
\author{Nafis Mustakin\\University of California, Riverside}
\date{October 2026}

\begin{document}

\maketitle

\begin{abstract}
A memory-aware scheduler needs to know how much memory a job uses over its run. \memprint{}, a Pin-based
footprint profiler, measures the pages a program touches, but its windowed mode costs $12.0\times$ a native run at
the median of 22 programs, $18.7\times$ to $93.0\times$ on programs that allocate and free memory often, and up to
$67.4\times$ on a language model engine. The resident set size (RSS) of a native run costs nothing extra, but it
overestimates allocator-heavy programs by a median of 16\% over the whole run, and miniVite by 102\%, because the
allocator keeps freed memory resident and RSS counts shared libraries. We propose a footprint model that samples, from
one thread inside the process every 5\,ms, the anonymous RSS, the proportional set size, the RSS of mapped data files,
and the free bytes the allocator reports (glibc, jemalloc or TCMalloc). Its data estimate, anonymous RSS minus free
bytes plus mapped data files and the runtime's pages, has a median whole-run error of $-4\%$ on the 7 allocator-heavy
programs of a 23-program corpus ($-7\%$ on miniVite), against $-5\%$ for \memprint{}, at a median of $0.99\times$ the
run time of a plain RSS run. Transferred from smaller inputs to a held-out larger one, it has a median error of
$-4\%$, against $+20\%$ for RSS and $-6\%$ for \memprint{}. In a cluster scheduling simulator that reserves memory by
each job's estimated curve, it gives the lowest mean response time of all estimates that profile the job's own input
(433 minutes at a load of 0.8, against 515 for the RSS curve and 519 for \memprint{}). Under TCMalloc its median
error is $-4\%$. Under jemalloc it is $-1\%$ with transparent huge pages disabled and $+35\%$ with them enabled,
because the kernel backs memory the program touches in part with whole 2\,MiB pages. On llama2.c and llama.cpp, the
data-file term brings the model from between $-39\%$ and $-92\%$ to between $-28\%$ and $+15\%$ of the truth.
The same library also measures which memory is cold, from the pages' accessed bits per call site and 2\,MiB chunk, at
$1.03\times$ to $1.21\times$ a native run. On a remote NUMA node that stands in for a memory pool, a plan built from
one profile run, even on a smaller input, keeps a quarter of the memory-time in the pool at $1.000\times$ to
$1.008\times$ the run time on GAP and CPython, where placing the hottest quarter costs up to $1.135\times$, and
moving memory between nodes during the run costs more than the plan. A latency model, checked at two pool latencies,
predicts that the plan costs at most $1.07\times$ on a pool at four times the local latency, where all memory in the
pool costs up to $1.94\times$; in a simulated cluster, the cold plan then runs 4\% more jobs per hour than a random
one.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A scheduler that packs jobs onto nodes by their memory use needs an estimate of each job's footprint over time,
because a job's peak lasts only part of its run~\cite{KSplus2024,Zacarias2021Accurate,Li2023Pond}. A reservation
that follows the footprint over time lets a node hold more jobs than a reservation of the peak, but the estimate
must not fall below what the job uses, or the job runs out of memory.

\memprint{} measures a program's footprint with Pin~\cite{Luk2005Pin}. It records the bytes and pages each program
touches and the time at which each block is freed. Its windowed mode watches 5\% of the run and costs $12.0\times$ a
native run at the median on 22 programs of our corpus. However, on the programs where a footprint estimate helps the
most, those that allocate and free memory throughout their run, the cost rises to $18.7\times$ to $93.0\times$,
because Pin instruments every memory access and every allocator call.

The resident set size of a native run is the obvious cheap alternative. On array programs, RSS is the footprint,
because these programs allocate their arrays once and touch them. On allocator-heavy programs, RSS overestimates the
footprint over the run by a median of 16\%, and by 102\% on miniVite~\cite{minivite}, because the kernel counts
memory that the program no longer uses.

In this work, we make the following contributions:
\begin{itemize}
\item We identify the parts of RSS that are not part of the footprint, freed memory that the allocator keeps
resident and the pages of shared libraries, and we measure their size per program (\secref{sec:gap}).
\item We propose a footprint model that combines RSS, PSS, the RSS of mapped data files and the allocator's free
bytes, sampled every 5\,ms from a thread inside the process through an \texttt{LD\_PRELOAD} library
(\secref{sec:model}).
\item We show on 23 programs that the model matches \memprint{}'s accuracy on the job's own input and on larger
inputs predicted from smaller ones, at a median of $0.99\times$ the cost of a plain RSS run, and that sampling every 1\,ms at the same cost corrects
the transfer from runs of a few milliseconds (\secref{sec:repeat} and \secref{sec:transfer}).
\item We show in a cluster scheduling simulator that the model's curve gives the lowest response time of all
estimates of the job's own input (\secref{sec:sched}).
\item We evaluate the model under jemalloc and TCMalloc and on two language model engines, and we show that
transparent huge pages are the remaining source of disagreement with a 4\,KiB pages-touched truth, which no
interface without privileges can resolve inside a huge page (\secref{sec:alloc} and \secref{sec:llm}).
\item We test four other ways to correct RSS, each alone, and show why each is less accurate
(\secref{sec:options}).
\item We use the model at run time in libmpr, our allocation-resizing runtime, to return glibc's free memory to the
kernel from \texttt{free}, which lowers the time-averaged RSS of the allocator-heavy programs by 4.4\% at a median
run time of $1.01\times$, half of what returning every free byte would give (\secref{sec:trim}).
\item We extend the sampling library to measure cold memory per call site from the pages' accessed bits, without
privileges, and we show on an emulated memory pool that a placement plan from one profile run, carried to a larger
input, keeps a quarter of a job's memory-time in the pool at 0 to 17\% of the cost of placing all of it there, that
moving memory during the run does not pay on our programs, and that libmpr applies the plan together with its
reservations (\secref{sec:place}).
\item We show that the model needs no earlier run of a job, that it is within a median of 2.0\% of the truth on the
blind programs of a companion study~\cite{memprintstatic}, that borrowing the growth of similar programs does not
beat proportional growth, that code embeddings do not capture growth either, and that the companion study's
interpreter predicts array programs with no run at all
(\secref{sec:general}).
\item We compare the costs and effects of the approaches to the gap between RSS and the footprint, from estimating it
to lowering it and reserving less than the request (\secref{sec:space}).
\end{itemize}

\section{Background: what RSS counts}
\label{sec:background}

The RSS of a process is the number of its pages in memory, which the kernel counts in three parts that
\texttt{/proc/pid/status} reports as \texttt{RssAnon}, \texttt{RssFile} and \texttt{RssShmem}:
\begin{equation}
\mathrm{RSS} = \mathrm{RSS}_{\mathrm{anon}} + \mathrm{RSS}_{\mathrm{file}} + \mathrm{RSS}_{\mathrm{shmem}} .
\end{equation}
An \term{anonymous} page is a page that no file backs. The heap, the stacks and the memory that \texttt{mmap} returns
with \texttt{MAP\_ANONYMOUS} are anonymous, which covers every block that \texttt{malloc} serves. The kernel fills an
anonymous page with zeros when the program first touches it, and if the kernel needs the page for something else, it
can only move the contents to swap. The \term{anonymous RSS}, $\mathrm{RSS}_{\mathrm{anon}}$, counts the anonymous pages
of the process that are in memory. An anonymous page enters RSS when the program first touches it and leaves when the
program or its allocator unmaps it or releases it with \texttt{madvise}. A \term{file-backed} page holds part of a
file, such as a page of a shared library's code or of a mapped data file. It enters RSS when any process reads it and
stays as long as it is mapped and the kernel does not reclaim it, which the kernel can do at any time by dropping the
page and reading it from the file again later. $\mathrm{RSS}_{\mathrm{shmem}}$ counts shared memory, such as
\texttt{/dev/shm} files and shared anonymous mappings, which none of our programs use. The \term{footprint} we estimate is the set of
pages the program has touched and not yet freed, plus the pages the runtime needs before the program starts. RSS
differs from the footprint in five ways.

\textbf{Allocator retention.} The C library does not return every freed block to the kernel. glibc's
\texttt{malloc} serves blocks below a threshold (128\,KiB, raised dynamically up to 32\,MiB) from its arenas, keeps
freed blocks in free lists for reuse, and releases memory only from the top of the heap when the free space there
exceeds the trim threshold~\cite{glibcmanual}. jemalloc and TCMalloc also release freed memory late or in
batches~\cite{Evans2006jemalloc,Hunter2021Temeraire}. A program that frees and allocates memory throughout its run
therefore holds freed pages in RSS. Each of these allocators reports the bytes it holds free through its own
interface.

\textbf{Shared libraries.} RSS counts every resident page of every mapped file, including the code of the C library,
the C++ runtime and, for MPI programs, the MPI library. These pages do not depend on the input, and other processes on
the node map the same pages. The \term{proportional set size} (PSS) of a process charges the process for each of its
resident pages in proportion to how many processes map that page. For a process whose resident pages form the set
$R$, with a page size of $s$ bytes,
\begin{equation}
\mathrm{PSS} = \sum_{p \in R} \frac{s}{n_p} ,
\end{equation}
where $n_p$ is the number of processes that map page $p$. The kernel computes this sum over the page tables of the
process when a program reads \texttt{/proc/pid/smaps} or \texttt{smaps\_rollup}, which is why PSS costs more to read
than the counters of \texttt{/proc/pid/status}. A page that only this process maps counts in full ($n_p = 1$), so
the anonymous pages of a process that does not share memory with its parent or children count in full, and PSS is
$\mathrm{RSS}_{\mathrm{anon}}$ plus each resident file-backed page divided by the number of processes that map it. The
PSS of all processes on a node sums to the memory of the resident pages they map, whereas their RSS counts each shared page once per process.

\textbf{Mapped data files.} A program that maps its input, such as a language model engine that maps its weights,
holds that input in file-backed pages. These pages are part of the footprint, unlike the pages of libraries.

\textbf{Language runtimes with their own allocators.} CPython's object allocator takes 256\,KiB arenas from the system
and returns an arena only when all its objects are freed. GCC's garbage-collected heap also maps its own pages. The C
library's statistics do not cover these allocators.

\textbf{Page size.} RSS counts whole pages. On our corpus, the 4\,KiB pages a program touches exceed the bytes it
touches by 1\% at the median, so we use the pages as the truth. With transparent huge pages~\cite{LinuxTHP}, the
kernel can back a 2\,MiB aligned range of anonymous memory with one huge page at the first touch, and RSS then counts
2\,MiB even if the program touches only part of the range~\cite{Kwon2016Ingens,Panwar2019HawkEye}. Our machine
enables transparent huge pages for all anonymous memory (the \texttt{always} setting).

\section{The footprint model}
\label{sec:model}

The model estimates a footprint curve from five quantities sampled at the same time inside the process. Let $A(t)$
be the anonymous RSS, $P(t)$ the PSS, $M(t)$ the RSS of mapped data files, $F(t)$ the bytes the allocator holds
free, and $B$ the runtime's own pages, the smallest RSS of an earlier run of the program, which is measured once per
program. The model gives two estimates.

\textbf{Estimate 1, the data footprint,} is
\begin{equation}
\hat{f}_1(t) = \max\bigl(A(t) - F(t),\,0\bigr) + M(t) + B .
\end{equation}
It counts the anonymous pages the allocator has not freed and the pages of mapped data files, and it leaves out the
pages of libraries. It estimates the memory that grows with the input, which is what a scheduler predicts and what
our truth measures.

\textbf{Estimate 2, the charged footprint,} is
\begin{equation}
\hat{f}_2(t) = \max\bigl(P(t) - F(t),\,0\bigr) .
\end{equation}
PSS is the anonymous RSS plus each file-backed page divided by the number of processes that map it, so the estimate
charges the job for its share of shared libraries and data files and for all of a library that only it maps. It
estimates the memory the job adds to a node.

Both estimates subtract free bytes from resident memory rather than count live allocations. A counter of live
\texttt{malloc} blocks misses every allocation that does not go through \texttt{malloc}, so an estimate built from it
falls below the truth whenever a program uses its own allocator. Subtracting free bytes errs the other way. Memory
that the allocator does not report stays in RSS, so a program whose allocator the model cannot see gets the RSS
estimate, which is too high but safe.

\begin{sloppypar}
\textbf{Free bytes.} The library looks up the allocator's interface when it starts. With jemalloc (\texttt{mallctl}),
the free bytes are \texttt{stats.resident} minus \texttt{stats.allocated} minus \texttt{stats.metadata}, after a
refresh of the statistics through \texttt{epoch}. With TCMalloc (\texttt{MallocExtension\_GetNumericProperty}), they
are \texttt{generic.heap\_size} minus \texttt{tcmalloc.pageheap\_unmapped\_bytes} minus
\texttt{generic.current\_allocated\_bytes}. Otherwise they are glibc's \texttt{mallinfo} field \texttt{fordblks}, the
free bytes of all its arenas. The machine runs glibc 2.28, which has no \texttt{mallinfo2}, so glibc's free bytes are
a 32-bit field that wraps above 4\,GiB. A newer glibc reports them in 64 bits.
\end{sloppypar}

\textbf{Mapped data files.} A data file is a file mapping that is not the executable, a shared object (a path that
contains \texttt{.so}), or the C library's locale and character set data. $M(t)$ is the sum of the RSS of these
mappings.

\textbf{Implementation.} A shared library of 162 lines of C, loaded with \texttt{LD\_PRELOAD}, starts one thread in
its constructor. Every 5\,ms the thread reads the process's memory counters, queries the allocator, and writes one line
to a buffered file. It has two modes. The first reads \texttt{/proc/self/smaps\_rollup}, which gives $A$, $P$ and RSS
but not $M$. The second reads \texttt{/proc/self/smaps}, one record per mapping, which also gives $M$. On the 23
corpus programs, $M$ is at most 0.07\,MiB, so we evaluate the corpus with the first mode and the language model
engines with the second. The thread does not stop the program's threads, and it takes the allocator's locks only for
the duration of its query. The library removes itself from \texttt{LD\_PRELOAD} so that child processes are not
sampled, and a program made of several processes would need one output file per process.

\section{Methodology}
\label{sec:method}

\textbf{Machine.} All runs use a two-socket Intel Xeon E5-2620 v4 (16 cores, 32 threads) with 62\,GiB of memory,
Linux 4.18 with transparent huge pages enabled, and glibc 2.28. Runs whose time we report execute one at a time on an
otherwise idle machine.

\textbf{Corpus.} We use the 23 programs of the corpus for which a pages-touched truth exists, each at its largest
input: PolyBench (2mm, atax, gemm, jacobi-2d), the NAS parallel benchmarks (cg, is, mg), the GAP benchmark suite (bfs,
cc, pr, sssp)~\cite{beamer2015gap}, the proxy applications HPCCG, Kripke, LULESH, miniFE, miniVite and Quicksilver,
darknet AlexNet inference, GCC's \texttt{cc1} compiling SQLite, and Lua~\cite{ierusalimschy1996lua}, CPython, Perl and
SQLite running table, JSON, hash and SQL workloads. We call 7 programs \term{allocator-heavy}, because they allocate
and free memory throughout their run: miniVite, CPython, Lua, SQLite, Perl, Quicksilver and \texttt{cc1}. We chose the
set before these experiments, from the earlier observation that RSS and \memprint{} disagree on these programs and
agree on the others. The runs last 0.1 to 12\,s and peak at 27 to 273\,MiB of RSS. Every program except darknet also
has one or two smaller inputs. Separately, we use llama2.c with three model sizes (15M, 42M and 110M parameters) and
llama.cpp with a 135M-parameter model generating 32 and 128 tokens.

\textbf{Truth.} The truth is the number of 4\,KiB pages the program touches and has not freed, which Pin measures in
\memprint{}'s splitter mode with page counting and free tracking, plus the runtime's pages $B$. Pin's time axis is
its count of memory references. We place the truth on the wall clock of a native run through hardware counts of the
loads and stores that the native run executes in every 5\,ms interval. The truth at a share $f$ of Pin's references is
placed at the time at which the native run had executed a share $f$ of its references. We divide each run into 100
equal steps of progress and take the largest value of each curve in each step. The estimates are placed on the same
100 steps by the wall clock of their own run. The truths under jemalloc and TCMalloc come from Pin runs with the same
allocator, and they are placed on the wall clock by the counts of the native run with glibc.

\textbf{Metrics.} We report three errors of an estimate $e$ against the truth $t$ over the 100 steps. The signed
whole-run error is $(\sum e - \sum t)/\sum t$, which is positive when the estimate reserves more memory over the run
than the program uses. The absolute whole-run error is $\sum |e - t| / \sum t$. The peak error is $\max e / \max t -
1$. Each program runs 3 times, and we report the median of each error over the runs. The overhead of an estimate is
the median wall time of its run over the median wall time of a run under the plain RSS sampler of the corpus
(\texttt{rss\_sampler.py}, an external process that reads \texttt{smaps\_rollup} every 5\,ms and takes 40\,ms to
start).

\textbf{Baselines.} \emph{RSS} is the RSS curve of the plain sampler's run. \emph{\memprint{}} is the windowed mode
that watches 5\% of the run (W5), placed on the native wall clock by the same reference counts as the truth, plus $B$.
Because the truth and \memprint{} pass through the same clock mapping, \memprint{}'s timing error against the truth
is smaller than its timing error against the real run. Its cost is the wall time of the W5 run and of the counter run
over the wall time of an earlier plain RSS run. \memprint{} has no W5 curve for darknet, so its rows cover 22
programs.

\textbf{Allocator-heavy programs.} The data estimate reduces the median whole-run error of RSS from $+16\%$ to $-4\%$
and the median absolute error from 17\% to 8\% (\tabref{tab:summary}). \memprint{} has a median signed error of
$-5\%$ and a median absolute error of 5\%. Per program (\tabref{tab:model}), the data estimate reduces miniVite's
error from $+102\%$ to $-7\%$, CPython's from $+25\%$ to $-3\%$, and Lua's from $+20\%$ to $-1\%$, and its absolute
error is at most 11\% on every allocator-heavy program. Its peak is within 4\% of the truth's on all 7 programs, with a
median of $-2\%$, while the RSS peak is 10\% too high at the median. \memprint{}'s lowest peak error is $-16\%$, on
Lua.

\textbf{The charged estimate.} The charged estimate has a median signed error of 0\% on the allocator-heavy programs,
and it lies above the truth on miniVite ($+37\%$), \texttt{cc1} ($+12\%$) and Quicksilver ($+8\%$), because it keeps
the pages of libraries that only this job maps. Unlike the data estimate, the charged estimate counts memory that the
truth does not count, so its error against the truth does not measure its accuracy as an estimate of a node's memory
use.

\textbf{Other programs.} On the 16 other programs, RSS is already accurate, with a median signed error of $+1\%$ and a
median absolute error of 2\%. The data estimate has $-1\%$ and 3\%, and \memprint{} has $-1\%$ and 1\%.

\textbf{The truth's clock.} An earlier version of this comparison kept the truth on Pin's count of memory references.
Every estimate then had whole-run errors of 10\% or more in the same direction on 7 of the 16 other programs, from
$+10\%$ to $+35\%$ on the GAP programs and from $-10\%$ to $-25\%$ on atax, NPB-IS and NPB-MG, with peak errors within
6\%. A phase that executes few memory references per second, such as GAP's graph construction, takes a smaller share
of the run on Pin's clock than on the wall clock. Placing the truth on the native wall clock removes these errors, and
the wall clock is the axis on which a scheduler observes a job.

\textbf{Overhead.} The model's run takes $0.99\times$ the time of a plain RSS run at the median, and $0.96\times$ to
$1.04\times$ on 20 of the 23 programs. The plain RSS run includes the 40\,ms that the external sampler takes to start,
which explains the ratios of $0.60\times$ for atax and $0.84\times$ for NPB-MG, whose runs last 0.10\,s and 0.31\,s.
darknet runs $1.21\times$ slower under the model in all 3 runs. A thread that sleeps for 0.99\,s between samples slows
darknet by the same $1.22\times$, so the cost comes from the presence of a second thread in a single-threaded program,
and not from the sampling. We did not identify which code path the second thread slows down. The mode that reads
\texttt{smaps} takes $0.98\times$ the time of a plain RSS run at the median ($0.60\times$ to $1.18\times$).
\memprint{}'s W5 run with its counter run takes $12.0\times$ a native run at the median, $8.9\times$ on the other
programs and $34.4\times$ on the allocator-heavy programs, with $93.0\times$ on \texttt{cc1}.

small inputs predicts the curve of a larger one. We apply one transfer rule, fixed before looking at the results, to
every estimate. The peak at the largest input is a linear regression of the smaller inputs' peaks on the input
size~\cite{KSplus2024}, never below the largest peak seen, and the shape is the curve of the largest smaller input,
scaled to that peak. The largest input is held out, and the model's smaller inputs run once each.

The data estimate transfers as accurately as \memprint{} (\tabref{tab:transfer}). On the allocator-heavy programs, its
median whole-run error is $-4\%$ (10\% absolute), against $+20\%$ (22\%) for RSS and $-6\%$ (10\%) for \memprint{}. On
the other programs, it is $-2\%$ (6\%), against $+2\%$ (10\%) for RSS and 0\% (5\%) for \memprint{}.

Three cases show where transfer fails. On \texttt{cc1}, every estimate is 226\% to 351\% too high, because the three
inputs are different source files whose size predicts the compiler's memory poorly. On NPB-MG, the data estimate is
67\% too low and RSS 96\% too low, because the only usable smaller input runs for a few milliseconds and the 5\,ms
sampling misses its peak, while \memprint{} counts every reference and is 15\% too high. On 2mm, gemm and jacobi-2d,
RSS is 25\% to 35\% too low for the same reason, because the smallest input's run fits in one sample of the external
sampler, which sees only the runtime. The model's thread starts before \texttt{main} and samples these runs, and its
error on them is $-10\%$ to $-4\%$. The transfer of a model trained on short runs therefore depends on how often it
samples the start of a run.

\textbf{Sampling short runs faster.} We tested three faster samplers, with a protocol committed before the runs
(\texttt{paper\_rss/sampling/PROTOCOL.md}), and rebuilt the transfer from each (\tabref{tab:sampling}). The first reads
\texttt{smaps\_rollup} every 1\,ms instead of every 5\,ms. The second reads the process's RSS counters from

A software page-fault event on each CPU (\texttt{perf\_event\_open}, inherited by the program's threads) wakes the
sampling thread after every 256 page faults, and the thread also samples every 5\,ms. Each sampler ran 3 times on every
smaller input. Sampling \texttt{smaps\_rollup} every 1\,ms reduces NPB-MG's error from $-50\%$ (in these runs, against
$-67\%$ in \tabref{tab:transfer}) to $+1\%$ and gemm's from $-9\%$ to $-3\%$, and it gives the lowest median error over

counters in batches, and the peak RSS that the kernel reports (\texttt{VmHWM}) is taken from the same counters. In a
test that touches 128\,KiB without huge pages, \texttt{RssAnon} did not change, while \texttt{smaps} counted the

peak, and \texttt{VmHWM} is 1.04\,MB. The page tables, which \texttt{smaps\_rollup} walks, are therefore the reference

program alone at the median, and the sampling thread's cost on darknet, $1.25\times$ to $1.27\times$, is the same for
every sampler (\secref{sec:repeat}).

We place the model's curves in DMSched-Sim, the trace-driven scheduling simulator of the corpus. The simulator replays
a synthetic job stream with MetaCentrum's shape (3000 jobs, 1 to 16 cores, run times of 5 to 720 minutes) on 32 nodes
with 32 cores and 128\,GB each and a 1\,TB memory pool. Each job takes the footprint curve of a random corpus program
with a smaller input, scaled to the job's peak, and the scheduler reserves memory by the oracle's estimate of that
curve. The reservation divides the run into 20 windows, holds the estimate's largest value in each window, widens each
window to its neighbours, and adds a margin times the peak. A job whose memory exceeds its reservation is killed, loses
its work, and is requeued with a reservation 1.5 times larger. Each oracle's margin is calibrated by leaving one
program out, so a job of program $p$ gets the 90th percentile of the margins the other programs need to never fall
below their truth.

On the pages truth (\tabref{tab:sched}), the data estimate gives the lowest mean response time of all estimates that
profile the job's own input, 433 minutes at a load of 0.8, against 515 for the RSS curve, 519 for \memprint{} on the
native clock and 479 for the exact peak. It also has the highest throughput of these estimates (44.9 jobs per hour)
and the fewest kills (319). Its calibrated margin is 7\%, against 12\% for \memprint{}, because no program needs a
margin above 9\% with it. \memprint{} on Pin's own clock gives 1607 minutes, because its curve and the job's footprint
disagree on when memory is used.

Every transferred estimate except \memprint{} on Pin's clock gives a response time at least twice that of the same
estimate on the job's own input. \memprint{} on the native clock transfers best (1283 minutes), and the data estimate
transfers worst (2806 minutes), although its median transfer error equals \memprint{}'s (\secref{sec:transfer}). The
calibrated margin follows the worst programs, and the data estimate needs a margin of 1.00 on gemm and 2.67 on NPB-MG,
the programs whose smaller inputs are too short for 5\,ms sampling, so its 90th percentile is 0.53, against 0.23 for
\memprint{}.

Under the RSS truth, which the kernel charges and OOM-kills on, the RSS curve of an earlier run is the best estimate
(393 minutes at a load of 0.8), because it measures the truth itself. The data estimate gives 748 minutes, close to
\memprint{} on the native clock (699 minutes), because it leaves out the retained memory and libraries that the RSS
truth counts, and its calibrated margin must cover them. The estimate a scheduler should use therefore depends on what
the node enforces. A limit on RSS calls for the RSS curve, and a limit on the memory the job uses, as in a cluster
whose allocators return freed memory, calls for the data estimate.

We ran the 7 allocator-heavy programs under jemalloc 5 and TCMalloc (gperftools 2.18, \texttt{tcmalloc\_minimal}),
loaded with \texttt{LD\_PRELOAD}, and measured the truth with Pin under the same allocator (\tabref{tab:alloc}).

\textbf{TCMalloc.} RSS overestimates the footprint by a median of 46\%, more than under glibc, because TCMalloc keeps
freed spans in its page heap and its caches. The data estimate has a median error of $-4\%$, and it is low on SQLite
($-22\%$) and miniVite ($-16\%$). Without the allocator's free bytes, the estimate is $+21\%$, so the statistics remove
most of the gap.

\textbf{jemalloc.} With transparent huge pages enabled, every estimate overestimates jemalloc's footprint, RSS by a
median of 56\% and the data estimate by 35\%, with $+149\%$ on miniVite. jemalloc places its extents at 2\,MiB aligned
addresses, so the kernel backs them with huge pages, and a 2\,MiB page counts in full when the program touches 4\,KiB
of it. In a run of Lua under jemalloc, 45\,MiB of the 65\,MiB of anonymous memory is in huge pages. We disabled
transparent huge pages for the process with \texttt{prctl(PR\_SET\_THP\_DISABLE)}, which the library calls in its
constructor on request. The data estimate's median error under jemalloc then drops to $-1\%$, and RSS's to $+26\%$.
Under TCMalloc and under glibc, disabling transparent huge pages changes the median errors by at most 4 points
(\tabref{tab:thp}).

The memory that huge pages add is real. A node with transparent huge pages enabled holds the whole 2\,MiB page in
memory, and the pages-touched truth undercounts it, as \memprint{} would. A scheduler on such a node needs the estimate
with huge pages, which the model measures and Pin does not, and a scheduler that wants the 4\,KiB footprint can disable
huge pages for the profiling run. We also checked two other kernel counters that we expected to matter.
\texttt{LazyFree}, the pages released with \texttt{MADV\_FREE} that stay resident until the kernel reclaims them, was 0
in the jemalloc runs, and the \texttt{Referenced} bytes of llama2.c's model file equal its RSS.

\textbf{How much huge pages add.} From the runs of \tabref{tab:alloc}, \tabref{tab:thp} and \secref{sec:llm}, we
divided each program's peak anonymous RSS with transparent huge pages enabled by its peak with them disabled. Under
glibc, the ratio is within 1.02 on 21 of the 23 programs, and huge pages add at most 2.6\,MiB, with $1.16\times$ on
miniVite and $1.04\times$ on Quicksilver. Under TCMalloc, the median ratio is 1.02. Under jemalloc, it is 1.17 (14.8\,MiB),
with $2.09\times$ on miniVite (29.5\,MiB). llama2.c's 42M and 110M models have ratios of $4.9\times$ and $5.2\times$,
24 and 47\,MiB of anonymous memory, but their RSS grows only $1.15\times$ and $1.14\times$, because the mapped model
file dominates it.

\textbf{Which 4\,KiB pages were touched.} A scheduler that wants the 4\,KiB footprint on a node with huge pages needs
to know which 4\,KiB pages of each huge page the program touched. We mapped 64\,MiB, touched one 4\,KiB page in each
2\,MiB, and read the interfaces that need no privileges (\texttt{paper\_rss/sampling/thp\_test.c}). With huge pages
enabled, \texttt{smaps} reports 64\,MiB of \texttt{Rss} and of \texttt{AnonHugePages}, and \texttt{mincore} reports
all 16{,}384 pages of the range as resident. With \texttt{MADV\_NOHUGEPAGE} on the range, or with huge pages disabled
for the process, all three report 128\,KiB. \texttt{/proc/pid/pagemap} gives page frame numbers only to a process with
\texttt{CAP\_SYS\_ADMIN}, and the idle page tracking of \texttt{/sys/kernel/mm/page\_idle} needs root. Without
privileges, the 4\,KiB footprint under huge pages is therefore measurable only by preventing huge pages in the
profiling run, with \texttt{MADV\_NOHUGEPAGE} or \texttt{PR\_SET\_THP\_DISABLE}.

\section{Programs and inputs not seen before}
\label{sec:general}

A companion study~\cite{memprintstatic} asks how \memprint{} can estimate the footprint of a program that has never
been traced, because \memprint{}'s sampled estimate needs a correction factor that is trained on full Pin traces of
the same program. It answers from source code, with an abstract interpreter that predicts the access counts of every
byte. The footprint model needs no such training, because it measures the job's own run, and its only per-program
quantity is the runtime's pages $B$, which \secref{sec:model} takes from an earlier plain run. This section asks
what the model needs for a program that has not run before, in three settings: a job that is measured in its own
run, the blind programs of the companion study, and a job whose larger input is predicted with the growth of other
programs.

The companion study's second family of methods borrows the model of a known program that is similar to the new one,
with similarity measured by a descriptor of memory behaviour~\cite{memprintstatic}. The analogue for the footprint
model is a program that has run once, at a small input, and whose larger input is to be predicted without its growth
being known. We predict the largest input's curve as the small run's curve scaled to the peak $p_S (x_L / x_S)^\beta$,
where $x$ is the input size, and we borrow the exponent $\beta$ from the programs that are known. Each known program's
$\beta$ is the slope of its log peak against its log input size over all its inputs. The nearest-program method takes
the $\beta$ of the program closest in a descriptor of the small run, made of six standardised features: the
allocator's share of RSS, the mean over the peak, the time of the peak, the share of the run near the peak, the
value at a tenth of the run, and the final value. The RBF method weights every known $\beta$ by its distance, as the
companion study does. We evaluate with each of the 22 programs that have a smaller input held out in turn
(\texttt{paper\_rss/borrow.py}, committed before the results).

Borrowing does not beat the exponent 1 (\tabref{tab:borrow}). From the smallest input, the proportional prediction
has a median absolute error of 12.4\%, against 34.0\% for the nearest program's $\beta$ and 26.9\% for the RBF
mixture. The descriptor ranks the known programs by how well their $\beta$ transfers with a median Spearman $\rho$ of
0.36, against 0.89 for the companion study's descriptor on its example. The smallest inputs of the four PolyBench
programs hold less data than the runtime's pages vary, so every method misses them by 94\% to 96\%, and their own
$\beta$ comes out near 3. With the run at the largest smaller input instead, which we chose after seeing these
results, the proportional prediction has a median of 4.1\%, against 9.5\% and 11.1\% for borrowing, and $\rho$ is
$-0.11$. Most programs grow with an exponent near 1 in their input size, because the input sizes we use count the
data, and the programs that do not, \texttt{cc1} (0.42), Quicksilver (0.65) and miniVite (0.78), are not closer to
each other in the descriptor than to the others. The companion study's descriptor is a spectrum of access counts,
which determines its correction factor directly, whereas the shape of a footprint curve does not determine how the
footprint grows with the input. The transfer from two smaller inputs of the same program (\secref{sec:transfer}) has
a median of 3.9\% and is the better use of two cheap runs.

The static features predict the terms better than every embedding (\tabref{tab:similar}). Their distance correlates
with the difference in $r$ ($\rho = 0.67$), $R'$ (0.54) and $\beta$ (0.56), and taking $R'$ from the nearest program

the programs that link large libraries, from the rest. The embeddings correlate with $r$ and $R'$ more weakly, and
not with $\beta$ ($-0.12$ to $0.05$, none significant). Neither the memory code nor the larger model changes this:
Qwen3-Embedding-8B has $\rho = 0.03$ on $\beta$ on the whole code and 0.02 on the memory code. An embedding's nearest program is almost always of
the same suite (GAP, NPB or PolyBench), so an embedding finds the program's family, but not how its memory grows with
the input.

from 45\% to 20\% to 24\%, but not the median, 4.3\% to 5.7\% against 3.8\% for $\beta = 1$. The change in the 90th

Quicksilver's $\beta$ of 0.65, and its error falls from $+45\%$ to $+17\%$. With all static features, MiniFE borrows
the same $\beta$ and its error grows from $+3\%$ to $-24\%$. The two largest errors, atax ($-94\%$) and NPB MG

has a 90th percentile of 26\%, above the static features' 20\% to 24\%, which also shows that the difference rests
on a few programs. Code similarity thus has a measurable relation to the terms, but over 22 programs it does not
predict $\beta$ more accurately than $\beta = 1$, and the model's own run at the job's input remains more accurate.

A program that has never run can be predicted only from its source. The companion study's interpreter runs C and C++
programs from \texttt{main} and reports the bytes that they touch~\cite{memprintstatic}, and the footprint model adds
the terms that the interpreter does not see from other programs' runs. We predict the footprint as the interpreter's
footprint $P$ plus $R$, the median of the other programs' runtime pages $B$, and the RSS as $P / (1 - r) + R'$, where
$r$ is the median share of the anonymous memory that the other programs' allocators hold free at their peak, and $R'$
is the median of their peak RSS minus their largest data estimate, the pages of their libraries
(\texttt{paper\_rss/zero.py}). Every term comes from other programs, and the program itself never runs. We first
learned $R$ as the median of the truth minus $P$ over the other programs, which absorbed the interpreter's own errors
on those programs and gave $R = -15$\,MB, and we replaced it with the definition above after seeing that result.

and sssp at scale 18, LULESH at $s = 60$ and NPB MG. HPCCG at $64^3$ exceeds the interpreter's recursion depth, with a
limit of 200{,}000 frames and a 512\,MB stack, although it ran at the companion study's $28^3$. NPB IS and CG at class

from a chain of random-number calls that the interpreter runs one at a time, 4\,hours already at class W. The other

the interpreter counts are the pages in use. $R$ is 1.7 to 1.9\,MB. On GAP, it is 40\% to 45\% too high: the
interpreter counts every byte that the run touches, and GAP's graph builder fills temporary edge lists that it frees
before the kernel runs. LULESH is 57\% too high for the same reason, because it allocates and frees its temporary
arrays of 8 values per element in every step (\secref{sec:general}). On NPB MG, it is 10.5\% low,
the interpreter's own error on MG. Because a C++ prediction has no timeline, it holds the peak over the whole run,
which reserves 194\% to 206\% too much on GAP and 147\% on LULESH over the run, whose footprint is low for most of it;

programs whose source the interpreter can execute. For every other program, the model's own run, or its transfer from
two smaller runs, is cheaper and more accurate.

Before we settled on the model, we tested four alternatives on the allocator-heavy programs under glibc, each on its
own (\tabref{tab:options}). The first, RSS minus glibc's free bytes, is the first half of the model.

\textbf{Releasing freed memory during the run.} Instead of subtracting free bytes, the program can return them to the
kernel, so that RSS drops when the program frees memory. We tested two ways. The first calls \texttt{malloc\_trim(0)}
every 5\,ms from a thread in the process, which releases the free pages inside every arena with \texttt{madvise}. The
second sets glibc's trim threshold to 0, which releases free memory at the top of the heap after every \texttt{free}.
Both reduce the median error less than subtracting free bytes, $+11\%$ and $+14\%$ against $+9\%$. A trim threshold of
0 releases only the top of the heap, which explains why it changes Lua's error by only 3 points. Both alternatives
also change the program's allocation behaviour, and the trim thread costs up to $1.10\times$ on Perl.

\textbf{Language runtime statistics.} For CPython, we sampled the free bytes of its object allocator (the arena bytes
minus the bytes in allocated blocks, from \texttt{sys.\_debugmallocstats}) from a thread started in
\texttt{sitecustomize}. For Lua, we sampled the heap size the garbage collector reports
(\texttt{collectgarbage("count")}) from a debug hook every $10^6$ virtual machine instructions. CPython's whole-run
signed error drops to $+5\%$, but its absolute error rises, which means that the estimate is too low in some parts of
the run and too high in others. We did not determine why. Lua's heap count leaves out the interpreter's own memory and
gives $-19\%$. The statistics exist only for these two programs, and GCC reports its heap only at the end of a
compilation.

\textbf{Referenced pages per window.} The kernel can clear the referenced bits of a process's pages
(\texttt{/proc/pid/clear\_refs}), after which \texttt{smaps\_rollup} counts the pages the process has touched since. We
cleared the bits 20 times per run and took the pages referenced in each window as the footprint of that window, in the
manner of a working set~\cite{denning1968}. The estimate falls below the truth by up to 70\% (miniVite), 68\%
(\texttt{cc1}) and 55\% (Quicksilver), because a page that the program holds but does not touch within a window is not
counted. A scheduler that reserved this estimate would run these programs out of memory.

\section{Returning free memory at run time}
\label{sec:trim}

The model's free bytes are memory that the program has freed and that the allocator keeps resident. A runtime that
reads the same statistics can return this memory to the kernel while the program runs, which lowers the RSS and the
memory that a system must provision for the job. We added the model to libmpr, the runtime of our allocation-resizing
study, which serves each allocation of at least 64\,KiB from a per-site reservation that \memprint{} profiles and
commits only the predicted part of the block. libmpr leaves smaller blocks to glibc, so these blocks hold the free
bytes that the model subtracts.

\textbf{Mechanism.} With a share $s$ set (\texttt{MPR\_TRIM}), libmpr compares glibc's resident free bytes with
$\max(s \cdot A, 1\,\mathrm{MB})$, where $A$ is the anonymous RSS that the kernel keeps as a counter in
\texttt{/proc/self/status}, and it calls \texttt{malloc\_trim(0)} when the free bytes exceed this threshold.
\texttt{malloc\_trim} releases the whole pages inside every free chunk of every arena with \texttt{madvise}. glibc
counts the released bytes as free after the trim, because they are free but no longer resident, so libmpr keeps the
free bytes at the last trim apart as released, and it lowers this count when the free bytes fall below it, which
means that the program has reused released memory. The resident free bytes are then the free bytes minus the
released bytes.

libmpr makes this check from \texttt{free}, which it already intercepts, and not from a thread. A second thread
turns off the paths that glibc takes in a single-threaded process, in which \texttt{stdio} and \texttt{malloc} skip
their locks. With a monitoring thread that never trims, darknet, which parses its files one character at a time,
runs $1.23\times$ slower, and with the check in \texttt{free} it runs at $0.96\times$. The resident free bytes grow
only by the bytes that the program frees, so \texttt{free} counts these bytes and makes the next check only after the
program has freed the distance between the resident free bytes and the threshold, and at least 1\,MB. A program that
frees memory in a short burst is therefore trimmed at the end of the burst and not at the next tick of a timer. A
thread is still available for the monitor that writes the model's estimate every 5\,ms, and it trims as well.

\textbf{Methodology.} We ran the 29 workloads of the resizing study: the 23 programs at their largest inputs, with
miniVite built with the resizing compiler pass, and six configurations of llama2.c and llama.cpp. Each workload ran
under six builds, glibc, libmpr with the reservations of its own input and libmpr with reservations profiled on
other inputs, each without and with trimming at $s = 0.1$, three times each, with RSS sampled every 20\,ms. Four
workloads ran at a time on the 32-core machine, which adds about 5\% of noise to each run time. Every run produced
the output of the glibc run. The libmpr of these runs read only part of llama.cpp's longest reservation lines, which
lowered its commit by 0.8 to 4.2\,MB and left its RSS unchanged (\secref{sec:place}). Trimming acts on RSS, so we
keep these runs.

\section{Hot and cold memory for a memory pool}
\label{sec:place}

A system with disaggregated memory gives each node local memory and a shared pool that is slower to
reach~\cite{Li2023Pond,Peng2020Underutilization}. The footprint model tells the system how much memory a job holds.
To place part of that memory in the pool without slowing the job, the system must also know which memory the job
touches rarely. Pin can record every access, but at the cost of \secref{sec:repeat}. In this section, we extend the
sampling library to measure, at about the cost of a native run, which of a job's memory is hot and which is cold, and
we test whether a placement plan built from one profile run lets a job keep a quarter or half of its memory in the
pool at a small cost in run time.

\subsection{Measuring hot and cold memory without privileges}

\textbf{Accessed bits.} The referenced-page alternative of \secref{sec:options} clears the accessed bits of the
process's pages by writing \texttt{1} to \texttt{/proc/self/clear\_refs}, which needs no privileges. In the new mode
(\texttt{MPR\_MODE=refs}), the library's thread reads \texttt{/proc/self/smaps} at the end of each window of $W$
seconds and then clears the bits. For each mapping, \texttt{Rss} counts its resident memory and \texttt{Referenced}
the resident memory touched since the last clear. We call the referenced bytes of a window \term{hot} and the rest
of the resident bytes \term{cold}. The library writes these per window for the heap, the other anonymous mappings,
the stacks, the program's data and code, and for each call site below. Our kernel (4.18) has no
DAMON~\cite{park2019damon}, and its idle-page tracking interface (\texttt{/sys/kernel/mm/page\_idle}) requires
root.

\textbf{Call sites.} The kernel reports accessed bits per mapping, so the library makes every large block a mapping
of its own. In a build with call sites, it serves each \texttt{malloc}, \texttt{calloc}, \texttt{realloc},
\texttt{posix\_memalign}, \texttt{aligned\_alloc} or \texttt{memalign} of at least 256\,KiB with its own
\texttt{mmap}, followed by an inaccessible guard page, because the kernel merges adjacent anonymous mappings. It also
records the program's own anonymous private mappings of at least 64\,KiB, which covers CPython's 256\,KiB arenas and
GCC's garbage-collected pages. Each block belongs to a site, the stack of up to 8 return addresses that
\texttt{backtrace} finds above the library's own frames, identified by a hash of each frame's object path and offset.
The hash does not depend on where the objects are loaded, so a site has the same identity in every run and on every
input. To find the cold parts of a large block, the library also splits each block into 2\,MiB chunks. It marks every
other chunk with \texttt{MADV\_DONTDUMP}, which changes no behavior that our programs use, but which keeps the kernel
from merging neighboring chunks, so that each chunk is a mapping of its own.

\subsection{Placement on an emulated pool}

\textbf{Emulation.} Our machine has two NUMA nodes, and we use the second as the pool. Every run binds its threads and
its memory to node 0 (\texttt{numactl --cpunodebind=0 --membind=0}, from a user installation of numactl), and a plan
binds chunks to node 1 with \texttt{mbind} and \texttt{MPOL\_BIND} when the library creates the block, before the
program touches it. The firmware's distance table gives 21 for node 1 against 10 for node 0. A pool behind CXL is
slower than one NUMA hop~\cite{Li2023Pond}, so the run times below are a lower bound on the cost of a placement;
\secref{sec:cxl} models a slower pool. Every
placement run turns off transparent huge pages for the process (\texttt{MPR\_NOTHP}) and records the bytes on each
node from \texttt{/proc/self/numa\_maps} every 0.25\,s.

\textbf{Plans.} A profile run with chunks gives, for each chunk, its memory-time, the sum of its resident bytes over
the windows, and its referenced memory-time, the sum of its referenced bytes. A plan ranks the chunks by their
referenced share, the referenced memory-time over the memory-time, and takes chunks until their memory-time reaches a
share $f$ of the memory-time of all anonymous memory. The \term{cold} plan takes the least referenced chunks first,
the \term{hot} plan the most referenced first, and the \term{random} plan a random order. All plans with the same $f$
place the same memory-time in the pool, so they differ only in which memory they place. A budget of bytes at the peak
would not do this on GAP, whose peak falls in the construction of the graph, before the kernel runs. A chunk is named
by its site, the order of its block among the site's blocks, and its position in the block. Each policy runs 5 times,
interleaved with the others, and we report the median run time over that of the run with no plan.

\textbf{Which memory goes to the pool matters.} On GAP and CPython, the cold plan keeps the run time within 1\% of
the run with no plan at $f = 0.25$, while the hot plan with the same memory-time in the pool costs up to
$1.117\times$ and all memory on node 1 costs up to $1.160\times$ (GAP pr, \tabref{tab:place-static}). On GAP, CPython
and Lua, the cold plan pays 0 to 17\% of the cost of placing all memory in the pool, and the hot plan 32\% to 73\%.
At $f = 0.5$, the cold plan costs at most $1.027\times$ on GAP and CPython. The memory that the cold plan places is
not idle: on GAP, 31\% to 34\% of its memory-time is referenced within a window, and the remote node serves these
accesses at a small cost. The random plan lies between the two. miniVite, Quicksilver and \texttt{cc1} run at most $1.016\times$ slower
with all memory in the pool, so their placement does not matter. On Perl, the plans can place only the 17\% of the
memory-time that call sites cover, and all three plans give the same chunks.

\textbf{Plans from a smaller input.} A plan named by the block's order and the chunk's position does not carry over
to a larger input, whose blocks are larger and more numerous. A \term{relative} plan instead names, for each site, the
ranges of the block, in 16 equal parts, to place, pooled over all the site's blocks. We profiled GAP at a scale of 16
and CPython and Lua at a quarter of the input, and applied the relative plans at a scale of 18 and at the full input.
On the larger input, 90\% to 100\% of the site memory-time comes from sites that the smaller run saw. The transferred
cold plan matches the plan from the same input on GAP and CPython, $1.000\times$ to $1.008\times$ at $f = 0.25$, and the
transferred hot plan still costs $1.135\times$ on GAP pr. The memory-time that the transferred plans place differs
from $f$ by up to 0.11 on CPython, where the cold plan at $f = 0.25$ places 14\% of the memory-time and the hot plan
31\%. On Lua, the plans cover the same few sites, and all three cost about $1.045\times$.

\subsection{Moving memory while the program runs}

A plan needs a profile run. A runtime could instead move memory between the nodes while the program runs, by scoring
each chunk from the accessed bits of the past windows and moving chunks with \texttt{mbind} and
\texttt{MPOL\_MF\_MOVE}, as tiered-memory systems do~\cite{Maruf2023TPP,Raybuck2021HeMem,Lee2023Memtis}. We tested
three policies in the library (\texttt{MPR\_MIGRATE}). Each window, a chunk's score is $\alpha$ times its referenced
share in the window plus $1 - \alpha$ times its previous score. The \term{fill} policy ($\alpha = 0.5$, windows of
0.1\,s) keeps the lowest-scored chunks in the pool up to $f$ of the anonymous RSS. The \term{threshold} policy moves
only chunks scored at most 0.1. The \term{slow} policy uses $\alpha = 0.1$ and windows of 0.25\,s, so that a chunk must
stay cold for several windows before it moves.

None of the three policies approaches the static plan (\tabref{tab:place-migrate}). Monitoring alone costs
$1.013\times$ to $1.055\times$ with windows of 0.1\,s and $1.010\times$ to $1.022\times$ with windows of 0.25\,s,
because each sample reads every mapping and clears every accessed bit. The fill policy costs $1.074\times$ to
$1.148\times$ at $f = 0.25$, more than placing all memory in the pool on four of the six programs. In the steady state of these
programs, too little memory stays cold for a window to fill the budget, so the policy places hot memory and moves it
back and forth. The threshold policy finds less than 3\% of the memory-time cold enough to move, so its cost is that
of monitoring. The slow policy moves 68 to 205\,MB per run and costs $1.034\times$ to $1.060\times$ at $f = 0.25$,
against $1.000\times$ to $1.026\times$ for the static plan, because it judges new chunks before their accesses begin. The
static plan places memory before the first touch, so it moves nothing, it ranks chunks over the whole run, and it
needs no monitoring. On runs of a few seconds, the profile run is therefore worth more than run-time migration. A
program whose phases last much longer than a window may favor migration, but we did not test one.

\subsection{Placement in libmpr}

\textbf{Mechanism.} libmpr already serves each large block of a site with a reservation from a mapping of its own, so
it can bind ranges of the block to the pool before the program touches them. We added placement lines to its
reservation format, \texttt{key place K lo$_1$ hi$_1$ \ldots}, which bind $K$ ranges of each block of the site, given as
shares of the block, to the pool node (\texttt{MPR\_PLACE}, \texttt{MPR\_NODE}). A line is independent of the site's
reservation, and a site with a placement line and no reservation is served and committed in full. libmpr also
intercepts \texttt{mmap} and places the program's own anonymous mappings by their caller's line. libmpr names a site by
its return address in its object file, with up to two frames above it as a context, so a converter
(\texttt{place\_lplans.py}) maps each profiled stack to libmpr's key, skips the frames of \texttt{operator new} in the
C++ runtime, and pools the stacks that share a key. GAP's stacks map to keys one to one, and CPython's 62 stacks and
Lua's 8 map to 31 and 6 keys. Finding a site's context takes a \texttt{backtrace} and two \texttt{dladdr} lookups,
which on CPython, with about 2{,}700 arena mappings per run, cost $1.04\times$ even with all memory left on node 0.
libmpr now caches the site of each context by its frame addresses, which brings this cost to $1.01\times$.

On llama.cpp, the reservations alone lower the anonymous memory from 202 to 22\,MB, because libmpr does not zero the
pages of the key-value cache that the program never touches, and they make the run $0.83\times$ as long. The rest of
its resident memory is the model's weights, which the engine maps from its file and which no plan places. The first
profile covered only 6.5\% of llama.cpp's memory-time, because the library did not intercept the aligned allocations
through which ggml allocates its buffers. With \texttt{posix\_memalign}, \texttt{aligned\_alloc} and \texttt{memalign}

of commit, because libmpr serves the sites they name in full, where it would otherwise leave them to glibc. Without
reservations, the cold plan alone gives most of the reservations' effect for the same reason: libmpr serves the plan's
sites, including the key-value cache, and does not zero their untouched pages.

\subsection{A slower pool}
\label{sec:cxl}

Node 1 is a pool one NUMA hop away: a pointer chase over 512\,MB takes 101\,ns per load on node 0 and 157\,ns on node
1, so the pool adds 56\,ns. Memory behind CXL adds more than a NUMA hop~\cite{Li2023Pond}, and our machine offers no
way for an unprivileged user to slow node 1 down (throttling the uncore clock needs the model-specific registers, and
Broadwell has no memory bandwidth allocation). We therefore model a slower pool from the runs we can make.

\textbf{Model.} For each program, the time a placement adds is the number of the program's reads that the pool serves
times the pool's added latency $d$ times a constant $s$, the inverse of the program's memory-level parallelism:
$T(d) = T(56\,\mathrm{ns}) + s\,N\,(d - 56\,\mathrm{ns})$. We count $N$ with \texttt{perf stat} in user mode, as the
reads (loads, stores' reads for ownership and prefetches) that missed the last-level cache and were served by node 1's
memory, and fit $s$ by least squares over the runs whose policies differ only in where the memory lies: for GAP,
CPython and Lua every plan against libmpr with no plan, since libmpr serves the same blocks under both; for darknet
and llama.cpp only all memory local against all memory in the pool, with and without the reservations, since there a
plan also makes libmpr serve the sites it names and skip zeroing their untouched pages. The same runs, five of each,
use the plans, libmpr and settings of \tabref{tab:place-libmpr} and \tabref{tab:place-combo}.

\textbf{Check.} To test the model at a second latency, we ran every configuration again with eight threads on node 1's
CPUs streaming over node 1's memory. The pointer chase then takes 209\,ns on node 1, so the pool adds 107\,ns, and
102.5\,ns on node 0. Predicted from the runs at 56\,ns alone, the slowdowns at 107\,ns are within 0.015 of the measured
ones at the median and within 0.02 to 0.07 for every program but GAP bfs (0.11), whose run without a plan itself slows
by 5\% beside the streaming threads (\tabref{tab:place-cxl}). The model errs high: the prediction exceeds the
measurement in 74\% of the configurations, by 0.013 on average, so the slowdowns it gives at higher latencies are, if
anything, too large. The streaming threads also take bandwidth from the pool, which the check therefore includes, but
a CXL link with less bandwidth than a socket's memory controllers could cost bandwidth-bound programs more than the
model says.

\textbf{The cold plan stays cheap on a slower pool.} At 300\,ns, about $4\times$ the local latency, placing all
anonymous memory in the pool costs $1.38\times$ to $1.94\times$ on GAP, $1.46\times$ on CPython and $2.31\times$ on Lua,
and the hot plan at $f = 0.25$ costs $1.17\times$ to $1.71\times$ on GAP. The transferred cold plan still costs
$1.03\times$ to $1.07\times$ on GAP and CPython, 4 to 11\% of the all-pool cost on GAP. The model's cost is linear in the
latency, so the slower pool widens the gap between the cold and the hot plan without changing their order. On Lua the
cold plan costs $1.26\times$ at 300\,ns; it already paid 35\% of the all-pool cost at 56\,ns, the most of any program.
With their reservations, darknet's cold plan, which places 70\,MB, costs $1.04\times$, and llama.cpp's, which places
8\,MB, $1.09\times$.

\textbf{The pool in the cluster.} The cluster simulation of \secref{sec:trim} charges a job that holds a share $f$ of
its memory-time in the pool a run time of $1 + \beta f$, with $\beta = 0.5$ for every job. We replaced this cost with
one measured per workload: we ran each of the 29 workloads under libmpr with all memory local, all memory on node 1,
and the random plan at $f = 0.25$ and the cold and hot plans at $f = 0.25$ and $0.5$, each made from the workload's own
profile, under \texttt{perf stat} as above (3 runs each, node 1 idle and busy). The model above gives each policy's
run time at an added latency $d$, and a job's cost at $f$ is interpolated between the measured plans, from no cost
at $f = 0$ to all memory in the pool at $f = 1$. Only the reads that a plan adds over the local run count, because
node 1 also holds the page cache of files that a local run maps, such as llama2.c's weights. Fitted on the idle
node, the model predicts the slowdowns on the busy node within 0.008 at the median. It errs most on HPCCG and NPB CG
(0.17 and 0.24), which stream through memory and slow down beside the streaming threads more than the pointer chase
does. Each job also reads the pool at its workload's measured rate per thread times its cores, so the cluster's
demand on the pool follows from the schedule. A pool of bandwidth $B$ then has the latency that node 1 measured at
the same share of its own bandwidth (53\,GB/s at most; the pointer chase takes 149\,ns idle and 205\,ns at
saturation), and above $B$ the pool's part of each run is stretched by the excess. We run the simulation at the idle
latency, take the mean demand over the steady part of the run, set the loaded latency from it, and run again, halving
the step, until the latency moves by less than 1\,ns; 1{,}285 of the 1{,}296 simulations with a bounded bandwidth
settle in 10 runs or fewer, and the other 11 alternate between two latencies 2\,ns apart.

\textbf{Minute by minute.} To see the peaks, we made the simulator set the pool's latency every minute. Each minute,
the jobs that run read the pool at their rates at the current latency; the sum gives the pool's latency and stretch
as above, and each job advances by $1 / (1 + e)$ minutes of its run with all memory local, where $e$ is its cost at
that latency. The scheduler commits a job's resources for the run time at the latency of the minute it starts; a job
that finishes early releases the rest, and one that runs longer keeps its last minute's resources one minute at a
time. In the 1{,}728 simulations, no extended job ever needed more cores than its node had. The pool's demand is
bursty (\tabref{tab:cxl-minute}): at 300\,ns it averages 12.5\,GB/s, but its 95th percentile is 27 to 28\,GB/s and
its largest minute 38 to 40\,GB/s, so a pool of 32\,GB/s is saturated in 2\% of the minutes and one of 16\,GB/s in
30\%, where the latency reaches that of node 1 at saturation. Where the pool is not saturated, the minute-by-minute
throughput agrees with the averaged one: over the configurations the two have in common, the difference is
$+0.1$ to $+0.3$ jobs per hour on average, below the standard deviation over seeds of 0.85. At 16\,GB/s, the
throughput falls by 1.0 jobs per hour with the cold plan against a pool of 256\,GB/s and by 1.2 and 1.5 with the
random and the hot plan, because the cold plan reads the pool least: at 16\,GB/s, the mean stretch of a job is 1.058
with the cold plan and 1.077 with the hot one. The bandwidth therefore matters only when the pool's bandwidth is near the jobs'
peak demand, and then a cold placement matters more, not less.

\textbf{A correction to the resizing runs.} While testing these changes, we found that libmpr read each reservation
line into a buffer of 512 bytes and dropped the rest of a longer line. The only lines this long are those of
llama.cpp's key-value cache, which list 60 to 120 ranges, of which libmpr kept the first 24. libmpr now reads lines of
up to 8{,}192 bytes and skips a longer line with a warning instead of reading part of it. With the whole lines, llama.cpp commits 0.7\,MB more at 32 tokens with the 135M model and 1.9\,MB
more at 64 tokens with the 360M model, and its RSS and output do not change. On the other 23 programs, the new
libmpr gives the same per-site commit, the same output and a peak commit 8\,KB higher than before. We ran the
resizing study's llama.cpp configurations again with the corrected libmpr (own, held-out and pooled reservations,
unseen inputs, the build with the pass, thread stacks and native profiles; 351 runs, every output identical): the
commit under libmpr rose by 0.4 to 2.7\,MB with each model's own profile and by up to 7.3\,MB with held-out and
pooled ones, whose lines are longer, and its commit stays 77 to 90\% below glibc's. The runs of
\secref{sec:trim} used the truncated lines too; they measure RSS, which the correction does not change, and we
keep them.

The approaches that we measured fall into four groups, which differ in what they change and in when they cost
(\tabref{tab:space}). The first group estimates the footprint for a scheduler and leaves the job's memory unchanged.
Its cost is paid once per program and input, and a production run costs nothing. The second group lowers the memory
that the job holds, by returning free memory to the kernel or by committing only the predicted part of each large
block. Its cost is paid on every run, and libmpr's reservations also need a profile. The third group changes the
scheduler, which reserves less than the request and resizes the reservation while the job runs, at the cost of
resizes and of restarts when a growth does not fit. The fourth group, placement, leaves the job's memory and the
scheduler's reservation unchanged and decides which part of the memory lies in a slower pool.

\textbf{Estimating the footprint.} The data estimate gives \memprint{}'s accuracy at the cost of a native run, and
the other cheap estimates are either less accurate (RSS, the trim alternatives) or below the footprint (referenced
pages), which a scheduler cannot use without a margin. Pin remains the only route to a per-site profile, and
\memprint{} costs $12.0\times$ at the median.

\textbf{Lowering the memory.} Each approach in this group acts on a different part of the waste. libmpr's
reservations act on the large blocks that the program requests and does not touch, which is where most of the
request's waste lies on this corpus: they raise the throughput from 21.7 to 25.0 jobs per hour without changing RSS.
Trimming acts on the small blocks that the program has freed. From \texttt{free}, it costs $1.01\times$ at the median
and returns half of the free memory, and the other half needs an allocator that can return memory in chunks smaller
than a page. The cost of such an allocator is the open question of this group. Mesh reports its own costs, and we did
not run it.

\textbf{Placing memory in a pool.} A static plan from one profile run places a quarter of the memory-time in the pool
at $1.00\times$ to $1.01\times$ on GAP and CPython, and it combines with libmpr's reservations: on darknet, the
reservations lower the commit by 47\% and the plan then lowers the local memory by 46\%, at $1.016\times$. Moving
memory while the program runs costs more than the static plan on every program we ran, and the monitoring alone costs
up to $1.06\times$.

\textbf{Reserving less.} Dynamic provisioning gains the most in response time, 1{,}844 to 1{,}129\,min, and its
costs are those of the cluster, resizes and restarts, and not of the job. The approaches combine. libmpr with
look-back dynamic provisioning gives 741\,min, and the bound on returning free memory lowers it to 559\,min, which is
below the 630\,min of the exact curve without libmpr. The exact curve with libmpr, 340\,min, is the limit that a
predicted curve would approach.

\section{Limitations}
\label{sec:limits}

A limitation of the free-byte correction is that it reads only the statistics of glibc, jemalloc and TCMalloc, which
leaves the memory of other allocators in the estimate. The arenas of CPython's object allocator and GCC's
garbage-collected heap stay in the estimate as RSS. On our corpus, the data estimate is nevertheless within 5\% of the
truth on CPython and \texttt{cc1}. Routing CPython's objects through glibc (\texttt{PYTHONMALLOC=malloc}) does not make
the estimate more accurate, and it changes the program. Under this setting, the data estimate's whole-run error is
$-2.5\%$ against a truth traced under the same setting, against $-2.9\%$ without it, while the truth's peak rises by
15\%, the run's peak RSS by 7\%, and its run time by $1.56\times$. On \texttt{cc1}, we counted GCC's own mappings by
interposing \texttt{mmap} and \texttt{munmap} in the sampling library. They hold 99\,MB of the 114\,MB of anonymous
memory at the peak, where glibc's free bytes are 2.8\,MB. GCC's statistics at the end of the compilation
(\texttt{-fmem-report}) show 12\,MB of the 94\,MB of its garbage-collected heap unused (13\%), which the data estimate
counts as data. It is unclear whether the 5\% result holds for inputs on which these allocators retain more memory.

A limitation of the data-file rule is that it classifies mappings by path, which counts any mapped file that is not a
shared object as data. A program that maps a large file it uses as code, or a library without \texttt{.so} in its
name, would have that file counted.

A limitation of the free-byte correction is also that some free bytes may not be resident, such as the untouched part
of the top of the heap, which makes the data estimate lower than the truth. The data estimate is below the truth on 6
of the 7 allocator-heavy programs under glibc, by 1\% to 9\% over the run, and on SQLite under TCMalloc by 22\%, so a
scheduler that uses it needs a margin.

A limitation of the sampling thread is that it adds a second thread to a single-threaded program, which slows darknet
by $1.21\times$ (\secref{sec:repeat}). Sampling from an external process avoids the thread, but the allocator's
statistics can be read only inside the process. libmpr's trimming avoids the thread by checking from \texttt{free}
(\secref{sec:trim}), but a monitor cannot, because it must sample while the program allocates without freeing. A second limitation of the thread is its 5\,ms interval, which misses
the curve of runs shorter than a few tens of milliseconds and limits the model's transfer from the smallest inputs
(\secref{sec:transfer} and \secref{sec:sched}). Sampling \texttt{smaps\_rollup} every 1\,ms at the same cost corrects
NPB-MG's transfer, but atax's transfer stays $-33\%$, and the kernel's cheaper RSS counters lag the page tables on runs
of a few milliseconds (\tabref{tab:sampling}).

A limitation of the placement study is its pool, a second NUMA node one hop away, which is faster than a pool
behind CXL. We model a slower pool from the counts of the reads the pool serves and check the model at a second,
measured latency, but the model is linear in the latency, misses part of the cost to programs that stream through
memory (HPCCG and NPB CG, by up to 0.24), and runs on a node
with CPUs, where the kernel's placement of its own memory differs from that on a CPU-less pool. Its runs last
1.5 to 4\,s, which favors a static plan over migration, and its plans place only blocks of 256\,KiB or more and the
program's own mappings, which leaves SQLite and most of Perl and Lua unplaced. Node 1 had about 400\,MB free, which
limited the inputs. The cluster simulation with the slower pool scales each job's cost and pool traffic from runs of
its workload and takes them as constant over the job's run, so the peaks of demand within a job are not modelled;
the pool's latency follows only the mix of jobs that run.

The evaluation covers a single machine, short runs of 0.1 to 12\,s and single-process programs. The truth's clock
mapping passes through the native run's reference counts, which also place \memprint{}'s curve, so \memprint{}'s timing
accuracy is overstated against the truth. The truths under jemalloc and TCMalloc use the clock of the native run under
glibc.

\section{Related work}
\label{sec:related}

\textbf{Footprint measurement.} Valgrind's Massif and DHAT~\cite{Nethercote2007Valgrind,dhat} and \memprint{} measure
the heap or the touched memory of every allocation by instrumenting the program. Our model reads counters that the
kernel and the allocator already keep. Unlike \memprint{}, it does not attribute memory to allocation sites or show
which bytes of a block the program touches.

\textbf{Page access sampling.} DAMON~\cite{park2019damon} and Thermostat~\cite{agarwal2017thermostat} sample the
accessed bits of pages to find cold memory, and PEBS sampling~\cite{roca_nonell2020pebs} records the addresses of
sampled loads. These methods measure which pages a program uses within a period of time, which is the working
set~\cite{denning1968} and not the footprint. Our referenced-page alternative (\secref{sec:options}) shows that the
working set of a window falls far below the footprint on allocator-heavy programs.

\textbf{Tiered memory.} TPP~\cite{Maruf2023TPP}, HeMem~\cite{Raybuck2021HeMem} and Memtis~\cite{Lee2023Memtis}
move pages between fast and slow memory while the program runs, from sampled accesses or the kernel's page faults,
and Pond~\cite{Li2023Pond} sizes a virtual machine's local memory and places the rest in a CXL pool. Our placement
decides per call site before the program runs, from one profile run, and our runs show that on short jobs this beats
moving memory from the accessed bits during the run.

\textbf{Memory prediction for scheduling.} KS+~\cite{KSplus2024} predicts a workflow task's memory over time from the
RSS of earlier runs, and Zacarias et al.~\cite{Zacarias2021Accurate,Zacarias2023Dynamic} predict the memory of HPC jobs
from earlier runs. Pond~\cite{Li2023Pond} predicts how much of a virtual machine's memory goes untouched. These systems
learn from RSS or from allocated memory, and our model gives them a training signal without the allocator's retained
memory and the job's shared libraries at the same cost as RSS.

\textbf{Allocators and huge pages.} Mesh~\cite{Powers2019Mesh} compacts the heap to return fragmented memory to the
kernel, and TCMalloc's Temeraire~\cite{Hunter2021Temeraire} releases free huge pages. Ingens~\cite{Kwon2016Ingens} and
HawkEye~\cite{Panwar2019HawkEye} limit the memory that huge pages waste on partly used ranges. These systems reduce the
gap between RSS and the footprint by changing the system, whereas our model measures the gap without changing the
program's allocations.

\section{Conclusion}
\label{sec:conclusion}

RSS overestimates the footprint of programs that allocate and free memory throughout their run, because the allocator
keeps freed memory resident and because RSS counts shared libraries. A model that subtracts the allocator's free bytes
from the anonymous RSS and adds mapped data files and the runtime's pages reduces the median whole-run error on these
programs from $+16\%$ to $-4\%$, which matches \memprint{}'s accuracy on the job's own input and on larger inputs, at a
median of $0.99\times$ the run time of a plain RSS run instead of $34.4\times$. In a scheduling simulation, its curve
gives the lowest response time of the estimates that profile the job's own input. Pin-based profiling remains needed
for attributing memory to code, for allocators the model cannot query, for the curves of runs too short to sample, and
for the 4\,KiB footprint of programs whose memory the kernel backs with huge pages. Used at run time, the same
statistics let a runtime return the allocator's free memory to the kernel, which lowers the RSS of allocator-heavy
programs by a few percent at no measurable cost, but which does not change the throughput of a cluster that already
resizes the large allocations. glibc returns only whole free pages, which is half of the free memory, and an allocator
that returned the rest would raise that cluster's throughput by 0.9 to 2.3 jobs per hour. The model needs no training on the program: it takes the runtime's pages from the job's own run, it measures the
companion study's blind programs within a median of 2.0\%, and for a program that cannot be run before it is
scheduled, the interpreter's footprint plus the runtime's pages of other programs predicts array programs within
1.1\% of the peak, but programs that free memory need the model's own run. Static features of the code and the
executable relate to the model's terms, and four code embeddings, up to 8B parameters, do not relate to how the
footprint grows with the input. The same library measures which memory is cold per call site at close to the cost of
a native run, and a plan from one profile run, carried to a larger input and applied by libmpr with its reservations,
keeps a quarter of a job's memory-time in a slower pool at a cost of at most 1\% on GAP and CPython, and a latency
model predicts at most 7\% on a pool four times slower than local memory. In a cluster simulation with these costs,
the pool's latency, not its bandwidth, sets the throughput, and placing the cold memory in the pool keeps one more
job per hour than a random placement at 300\,ns.
