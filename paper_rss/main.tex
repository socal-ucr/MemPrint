\title{Memory Footprints from Resident Memory and Allocator Statistics:\\
A Footprint Model at the Cost of a Native Run}
\author{Nafis Mustakin\\University of California, Riverside}
\date{October 2026}

\begin{document}
\setlength{\emergencystretch}{3em}
\maketitle

\begin{abstract}
A memory-aware scheduler needs to know how much memory a job uses over its run. \memprint{}, a Pin-based
footprint profiler, measures the pages and bytes a program touches, but its windowed mode costs $12.0\times$ a
native run at the median of 22 programs and $18.7\times$ to $93.0\times$ on programs that allocate and
free memory often. The resident set size (RSS) of a native run costs nothing extra and matches the pages a program
touches on array programs, but it overestimates allocator-heavy programs by a median of 17\% over the whole run,
and by 99\% on miniVite. We show that the gap has two sources that a program can report about itself cheaply. First, the allocator keeps freed memory resident, and glibc reports the amount through
\texttt{mallinfo}. Second, RSS counts the pages of shared libraries, which do not grow with the input and are
shared with other processes. We propose a footprint model that samples, from one thread inside the process every
5\,ms, the anonymous RSS, the proportional set size (PSS) and glibc's free bytes, and that estimates either the
program's data footprint (anonymous RSS minus free bytes, plus the runtime's own pages) or its charged footprint
(PSS minus free bytes). On the 7 allocator-heavy programs, the data estimate reduces the median whole-run error from
$+17\%$ to $-4\%$ and the median absolute error from 20\% to 9\%, and it reduces miniVite's error from $+99\%$ to
$-8\%$. Its accuracy matches \memprint{}'s ($-6\%$ signed, 12\% absolute) at a median of $0.99\times$ the run
time of a plain RSS run (up to $1.21\times$, on darknet), against $34.4\times$ for \memprint{}. On the 16 other programs, it matches RSS. We also test the
alternatives one at a time. Releasing freed memory to the kernel during the run removes less of the gap,
language runtime statistics fit only two programs, and per-window referenced pages underestimate by up to 70\%.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A scheduler that packs jobs onto nodes by their memory use needs an estimate of each job's footprint over time,
because a job's peak lasts only part of its run~\cite{KSplus2024,Zacarias2021Accurate,Li2023Pond}. A reservation
that follows the footprint over time lets a node hold more jobs than a reservation of the peak, but the estimate
must not fall below what the job uses, or the job runs out of memory.

\memprint{} measures a program's footprint with Pin~\cite{Luk2005Pin}. It records the bytes and pages each
program touches and the time at which each block is freed. Its windowed mode watches 5\% of the run and costs
$12.0\times$ a native run at the median on the 22 programs of our corpus that it ran on. However, on the programs where a footprint estimate helps
the most, those that allocate and free memory throughout their run, the cost rises to $18.7\times$ to
$93.0\times$, because Pin instruments every memory access and every allocator call.

The resident set size of a native run is the obvious cheap alternative. On array programs, RSS is the footprint,
because these programs allocate their arrays once and touch them. On allocator-heavy programs, RSS overestimates
the footprint over the run by a median of 17\%, and by 99\% on miniVite~\cite{minivite}, because the kernel
counts memory that the program no longer uses.

In this work, we make the following contributions:
\begin{itemize}
\item We identify the two parts of RSS that are not part of the footprint on our corpus, freed memory that
glibc keeps resident and the pages of shared libraries, and we measure their size per program
(\secref{sec:background}).
\item We propose a footprint model that combines RSS, PSS and glibc's free bytes, sampled every 5\,ms from a
thread inside the process through an \texttt{LD\_PRELOAD} library, with two estimates for two uses
(\secref{sec:model}).
\item We show on 23 programs that the model matches \memprint{}'s accuracy on allocator-heavy programs and
matches RSS on the others, at a median of $0.99\times$ the run time of a plain RSS run
(\secref{sec:results}).
\item We test four other ways to close the gap, each alone, and show why each is less accurate
(\secref{sec:options}).
\end{itemize}

\section{Background: what RSS counts}
\label{sec:background}

The RSS of a process is the number of its pages in memory. An anonymous page enters RSS when the program first
touches it and leaves when the program or its allocator unmaps it or releases it with \texttt{madvise}. A
file-backed page, such as a page of a shared library's code, enters RSS when any process reads it and stays as long
as it is mapped and the kernel does not reclaim it. The \term{footprint} we estimate is the set of pages the
program has touched and not yet freed, plus the pages the runtime needs before the program starts. The truth in
our evaluation is this footprint as \memprint{} measures it (\secref{sec:method}). RSS differs from it in four
ways.

\textbf{Allocator retention.} The C library does not return every freed block to the kernel. glibc's
\texttt{malloc} serves blocks below a threshold (128\,KiB, raised dynamically up to 32\,MiB) from its arenas, keeps
freed blocks in free lists for reuse, and releases memory only from the top of the heap when the free space there
exceeds the trim threshold~\cite{glibcmanual}. Other allocators also release freed memory late or in
batches~\cite{Evans2006jemalloc,Hunter2021Temeraire}. A program that frees and allocates memory throughout its run
therefore holds freed pages in RSS. glibc reports the free bytes of all its arenas through \texttt{mallinfo} (the
field \texttt{fordblks}).

\textbf{Shared libraries.} RSS counts every resident page of every mapped file, including the code of the C
library, the C++ runtime and, for MPI programs, the MPI library. These pages do not depend on the input, and other
processes on the node map the same pages. The PSS of a process divides each resident page by the number of
processes that map it.

\textbf{Language runtimes with their own allocators.} CPython's object allocator takes 256\,KiB arenas from the
system and returns an arena only when all its objects are freed. GCC's garbage-collected heap also maps its own
pages. glibc's statistics do not cover these allocators.

\textbf{Page granularity.} RSS counts whole pages, and a program may touch part of a page. On our corpus, the pages
a program touches exceed the bytes it touches by 1\% at the median, so we use the pages as the truth.

\section{The footprint model}
\label{sec:model}

The model estimates a footprint curve from four quantities sampled at the same time inside the process. Let $A(t)$
be the anonymous RSS, $P(t)$ the PSS, $F(t)$ the bytes free in glibc's arenas, and $B$ the runtime's own pages, the
smallest RSS of an earlier run of the program, which is measured once per program. The model gives two estimates.

\textbf{Estimate 1, the data footprint,} is
\begin{equation}
\hat{f}_1(t) = \max\bigl(A(t) - F(t),\,0\bigr) + B .
\end{equation}
It counts the anonymous pages the allocator has not freed, and it leaves out file-backed pages. It estimates the
memory that grows with the input, which is what a scheduler predicts and what our truth measures.

\textbf{Estimate 2, the charged footprint,} is
\begin{equation}
\hat{f}_2(t) = \max\bigl(P(t) - F(t),\,0\bigr) .
\end{equation}
PSS is the anonymous RSS plus each file-backed page divided by the number of processes that map it, so the
estimate charges the job for its share of shared libraries and for all of a library that only it maps. It
estimates the memory the job adds to a node.

Both estimates subtract free bytes from resident memory rather than count live allocations. A counter of live
\texttt{malloc} blocks misses every allocation that does not go through \texttt{malloc}, so an estimate built from
it falls below the truth whenever a program uses its own allocator. Subtracting free bytes errs the other way. Memory
that glibc does not know about stays in RSS, so a program whose allocator glibc cannot see gets the RSS estimate,
which is too high but safe.

\textbf{Implementation.} A shared library of 100 lines of C, loaded with \texttt{LD\_PRELOAD}, starts one thread in
its constructor. Every 5\,ms the thread reads \texttt{/proc/self/smaps\_rollup} for the RSS, PSS and anonymous RSS,
calls \texttt{mallinfo}, and writes one line to a buffered file. The thread does not stop the program's threads,
and it takes glibc's arena locks only for the duration of \texttt{mallinfo}. The machine runs glibc 2.28, which
has no \texttt{mallinfo2}, so the free bytes are a 32-bit field that wraps above 4\,GiB. A newer glibc reports them
in 64 bits. The library removes itself from \texttt{LD\_PRELOAD} so that child processes are not sampled, and a
program made of several processes would need one output file per process.

\section{Methodology}
\label{sec:method}

\textbf{Machine.} All runs use a two-socket Intel Xeon E5-2620 v4 (16 cores, 32 threads) with 62\,GiB of memory,
Linux 4.18 and glibc 2.28. Runs execute one at a time on an otherwise idle machine.

\textbf{Corpus.} We use the 23 programs of the corpus for which a pages-touched truth exists, each at its largest
input: PolyBench (2mm, atax, gemm, jacobi-2d), the NAS parallel benchmarks (cg, is, mg), the GAP benchmark suite
(bfs, cc, pr, sssp)~\cite{beamer2015gap}, the proxy applications HPCCG, Kripke, LULESH, miniFE, miniVite and
Quicksilver, darknet AlexNet inference, GCC's \texttt{cc1} compiling SQLite, and Lua~\cite{ierusalimschy1996lua},
CPython, Perl and SQLite running table, JSON, hash and SQL workloads. We call 7 programs
\term{allocator-heavy}, because they allocate and free memory throughout their run: miniVite, CPython, Lua,
SQLite, Perl, Quicksilver and \texttt{cc1}. We chose the set before these experiments, from the earlier
observation that RSS and \memprint{} disagree on these programs and agree on the others. The runs last 0.1 to
12\,s and peak at 27 to 273\,MiB of RSS.

\textbf{Truth.} The truth is the number of 4\,KiB pages the program touches and has not freed, which Pin measures in
\memprint{}'s splitter mode with page counting and free tracking, plus the runtime's pages $B$. The truth's time axis
is Pin's count of memory references. We divide each run into 100 equal steps of progress and take the largest value
of each curve in each step. The estimates are placed on the same 100 steps by the wall clock of their own run.

\textbf{Metrics.} We report three errors of an estimate $e$ against the truth $t$ over the 100 steps. The signed
whole-run error is $(\sum e - \sum t)/\sum t$, which is positive when the estimate reserves more memory over the
run than the program uses. The absolute whole-run error is $\sum |e - t| / \sum t$. The peak error is
$\max e / \max t - 1$. Each program runs 3 times, and we report the median of each error over the runs. The
overhead of an estimate is the median wall time of its run over the median wall time of a run under the plain RSS
sampler of the corpus (\texttt{rss\_sampler.py}, an external process that reads \texttt{smaps\_rollup} every 5\,ms).

\textbf{Baselines.} \emph{RSS} is the RSS curve of the plain sampler's run. \emph{\memprint{}} is the windowed mode
that watches 5\% of the run (W5), placed on the native wall clock by the hardware counts of loads and stores of a
native run, plus $B$. Its cost is the wall time of the W5 run and of the counter run over the wall time of an earlier
plain RSS run. \memprint{} has no W5 curve for darknet, so its rows cover 22 programs.

\textbf{Accuracy on allocator-heavy programs.} The data estimate reduces the median whole-run error of RSS from
$+17\%$ to $-4\%$ and the median absolute error from 20\% to 9\% (\tabref{tab:summary}). Its accuracy matches
\memprint{}'s, which has a median signed error of $-6\%$ and a median absolute error of 12\%. Per program
(\tabref{tab:model}), the data estimate reduces miniVite's error from $+99\%$ to $-8\%$, CPython's from $+30\%$
to $+1\%$, and Lua's from $+23\%$ to $+1\%$, and its absolute error is at most 14\% on every allocator-heavy
program. Its peak is within 4\% of the truth's on all 7 programs, with a median of $-2\%$, while the RSS peak is
10\% too high at the median and 58\% too high on miniVite.

\textbf{The charged estimate.} The charged estimate lies above the truth on 5 of the 7 programs, with a median
signed error of $+7\%$, because it keeps the pages of libraries that only this job maps. On miniVite, these pages
belong to the MPI and PMIx libraries (\secref{sec:gap}), and the estimate is $+36\%$. Unlike the data estimate,
the charged estimate counts memory that the truth does not count, so its error against the truth does not measure
its accuracy as an estimate of a node's memory use.

\textbf{Programs that RSS already estimates.} On the 16 other programs, the model's estimates match RSS. Their
median signed errors are $-1\%$ (data) and $-4\%$ (charged), against $0\%$ for RSS
(\tabref{tab:summary}). The median absolute error is 12\% for the data estimate and 8\% for RSS, but this
difference comes from run-to-run variation and not from the model. The RSS that the model's own runs record has a
median absolute error of 11.5\% on the same programs, and the data estimate of the same runs has 12\%.

\textbf{Errors that every estimate shares.} On 7 of the 16 other programs, every estimate, \memprint{} included,
has a whole-run error of 10\% or more in the same direction. The GAP programs are overestimated by $+10\%$ to $+35\%$,
and atax, NPB-IS and NPB-MG are underestimated by $-10\%$ to $-25\%$. The peak errors of the same estimates are
within 6\%, so the estimates and the truth agree on the amount of memory and disagree on when it is used. The truth
is on Pin's count of memory references, and the estimates are on the wall clock, so a phase that executes few
memory references per second, such as GAP's graph construction, takes a larger share of the run on the wall clock.
The errors therefore measure the difference between the two clocks, and they bound the accuracy any wall-clock
estimate can show against this truth.

\textbf{Overhead.} The model's run takes $0.99\times$ the time of a plain RSS run at the median, and $0.96\times$
to $1.04\times$ on 20 of the 23 programs. The plain RSS run includes the 40\,ms that the external sampler takes to
start, which explains the ratios of $0.60\times$ for atax and $0.84\times$ for NPB-MG, whose runs last 0.10\,s and
0.31\,s. darknet runs $1.21\times$ slower under the model in all 3 runs. A thread that sleeps for 0.99\,s between
samples slows darknet by the same $1.22\times$, so the cost comes from the presence of a second thread in a
single-threaded program, and not from the sampling. We did not identify which code path the second thread slows
down. \memprint{}'s W5 run with its
counter run takes $12.0\times$ a native run at the median, $8.9\times$ on the other programs and $34.4\times$ on
the allocator-heavy programs, with $93.0\times$ on \texttt{cc1}.

Before we settled on the model, we tested four alternatives on the allocator-heavy programs, each on its own
(\tabref{tab:options}). The first, RSS minus glibc's free bytes, is the first half of the model.

\textbf{Releasing freed memory during the run.} Instead of subtracting free bytes, the program can return them to
the kernel, so that RSS drops when the program frees memory. We tested two ways. The first calls
\texttt{malloc\_trim(0)} every 5\,ms from a thread in the process, which releases the free pages inside every
arena with \texttt{madvise}. The second sets glibc's trim threshold to 0, which releases free memory at the top of
the heap after every \texttt{free}. Both reduce the median error less than subtracting free bytes, $+13\%$ and
$+16\%$ against $+12\%$. A trim threshold of 0 releases only the top of the heap, which explains why it changes
Lua's and SQLite's errors by less than 4 points. Both alternatives also change the program's allocation behaviour,
and the trim thread costs up to $1.10\times$ on Perl.

\textbf{Language runtime statistics.} For CPython, we sampled the free bytes of its object allocator (the arena
bytes minus the bytes in allocated blocks, from \texttt{sys.\_debugmallocstats}) from a thread started in
\texttt{sitecustomize}. For Lua, we sampled the heap size the garbage collector reports
(\texttt{collectgarbage("count")}) from a debug hook every $10^6$ virtual machine instructions. CPython's
whole-run signed error drops to $+9\%$, but its absolute error rises to 44\%, which means that the estimate is too
low in some parts of the run and too high in others. We did not determine why. Lua's heap count leaves out the
interpreter's own memory and gives $-18\%$. The statistics exist only for these two programs, and GCC reports its
heap only at the end of a compilation.

\textbf{Referenced pages per window.} The kernel can clear the referenced bits of a process's pages
(\texttt{/proc/pid/clear\_refs}), after which \texttt{smaps\_rollup} counts the pages the process has touched since.
We cleared the bits 20 times per run and took the pages referenced in each window as the footprint of that window,
in the manner of a working set~\cite{denning1968}. The estimate falls below the truth by up to 70\% (miniVite),
69\% (\texttt{cc1}) and 56\% (Quicksilver), because a page that the program holds but does not touch within a
window is not counted. A scheduler that reserved this estimate would run these programs out of memory.

\section{Limitations}
\label{sec:limits}

A limitation of the free-byte correction is that it reads only glibc's statistics, which leaves the memory of
other allocators in the estimate. A program linked with jemalloc or TCMalloc needs that allocator's own
statistics~\cite{Evans2006jemalloc,Hunter2021Temeraire}, and the arenas of CPython's object allocator and GCC's
garbage-collected heap stay in the estimate as RSS. On our corpus, the data estimate is nevertheless within 7\% of
the truth on CPython and \texttt{cc1}, and it is unclear whether this result holds for inputs on which these
allocators retain more memory.

A limitation of the data estimate is that it leaves out all file-backed pages, which is wrong for a program whose
data is a mapped file. A language model server that maps its weights, for example, holds most of its footprint in
file-backed pages. The charged estimate counts these pages, and we leave a rule that separates a program's data
files from its libraries for future work.

A limitation of the free-byte correction is also that some free bytes may not be resident, such as the untouched
part of the top of the heap, which makes the data estimate lower than the truth. The data estimate is below the
truth on 4 of the 7 allocator-heavy programs, by $-4\%$ to $-8\%$ over the run, and its peak is at most 4\% low, so
a scheduler that uses it needs a headroom of a few percent.

A limitation of the sampling thread is that it adds a second thread to a single-threaded program, which slows
darknet by $1.21\times$ (\secref{sec:results}). Sampling from an external process avoids the thread, but glibc's
statistics can be read only inside the process, and we leave a design without a thread for future work.

The evaluation covers a single machine, short runs of 0.1 to 12\,s, single-process programs, and estimates of the
same input as the run. It does not test whether the model's curve from a small input transfers to a larger input, or
how a scheduler performs with the model's estimates, and we leave both for future work. The truth's clock of
memory references also limits the accuracy that any wall-clock estimate can show (\secref{sec:results}).

\section{Related work}
\label{sec:related}

\textbf{Footprint measurement.} Valgrind's Massif and DHAT~\cite{Nethercote2007Valgrind,dhat} and \memprint{}
measure the heap or the touched memory of every allocation by instrumenting the program. Our model reads counters that the kernel and glibc already keep. Unlike \memprint{}, it
does not attribute memory to allocation sites or show which bytes of a block the program touches.

\textbf{Page access sampling.} DAMON~\cite{park2019damon} and Thermostat~\cite{agarwal2017thermostat} sample
the accessed bits of pages to find cold memory, and PEBS sampling~\cite{roca_nonell2020pebs} records the addresses
of sampled loads. These methods measure which pages a program uses within a period of time, which is the
working set~\cite{denning1968} and not the footprint. Our referenced-page alternative (\secref{sec:options}) shows
that the working set of a window falls far below the footprint on allocator-heavy programs.

\textbf{Memory prediction for scheduling.} KS+~\cite{KSplus2024} predicts a workflow task's memory over time from
the RSS of earlier runs, and Zacarias et al.~\cite{Zacarias2021Accurate,Zacarias2023Dynamic} predict the memory of
HPC jobs from earlier runs. Pond~\cite{Li2023Pond} predicts how much of a virtual machine's memory goes untouched.
These systems learn from RSS or from allocated memory, and our model gives them a training signal without the
allocator's retained memory and the job's shared libraries at the same cost as RSS.

\textbf{Allocators that return memory.} Mesh~\cite{Powers2019Mesh} compacts the heap to return fragmented memory
to the kernel, and TCMalloc's Temeraire~\cite{Hunter2021Temeraire} releases free huge pages. These allocators reduce
the gap between RSS and the footprint by changing the program, whereas our model measures the gap without changing
the program's allocations.

\section{Conclusion}
\label{sec:conclusion}

RSS overestimates the footprint of programs that allocate and free memory throughout their run, because glibc keeps
freed memory resident and because RSS counts shared libraries. A model that subtracts glibc's free bytes from the
anonymous RSS and adds the runtime's own pages reduces the median whole-run error on these programs from $+17\%$ to
$-4\%$, which matches \memprint{}'s accuracy, at a median of $0.99\times$ the run time of a plain RSS run instead
of $34.4\times$. On array programs, it matches RSS. Pin-based profiling is therefore needed for attributing memory to
code and for allocators that glibc cannot see, and not for the footprint curve a scheduler uses.

\texttt{\textasciitilde/memprint-data/2026-10-26-rsscurve/opts}.
