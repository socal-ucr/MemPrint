\author{Nafis Mustakin\\University of California, Riverside}
\date{October 2026}

\begin{abstract}
A CUDA program runs as a sequence of operations on the GPU: kernel launches, copies between host and device
memory, and memory fills. One operation depends on an earlier one when it reads bytes the earlier one wrote, or
writes bytes the earlier one read or wrote. A runtime system that knows these dependences can run independent
operations at the same time or reorder them, but in graph programs and other irregular code the bytes a kernel
touches are chosen by values in memory, such as the neighbour lists of a graph, so a compiler cannot determine them
from the source code. We present two interpreters that determine them before the program runs on the GPU, from the
program's CUDA source and its input. The whole-program interpreter runs host code and kernels from source on the
CPU. The hybrid interpreter runs the host code natively, compiled against a stand-in CUDA runtime whose device
memory is host memory, and interprets each kernel on the real memory contents. Both run all threads of a kernel at
once as arrays, so a value loaded from memory, a branch on it and an address computed from it are known exactly.
When threads load pointers to different buffers, the interpreter splits them into groups by buffer. When the bytes a
kernel touches depend on the order in which threads run, the interpreter runs several legal thread orders, reports a
dependence as certain only if every order produces it, and adds every dependence any order could produce as
possible, generalised over the number of rounds a loop on the host runs. We compare the interpreters against the
bytes each operation touched on an NVIDIA A30, recorded with an NVBit tool. On \numBenchHyDone{} unmodified programs
from Rodinia, GraphBIG and PolyBench-GPU, the hybrid interpreter reports none of the GPU's \numBenchHyTruth{}
dependences wrongly and misses none: \numBenchHyCertTP{} are reported as certain and \numBenchHyPossYes{} as possible,
and it reports \numBenchHyPossNo{} possible dependences that the traced run did not have, all in programs whose
behaviour depends on thread order or that read past the end of a buffer. The whole-program interpreter is exact on
the \numBenchFuNoFN{} programs whose host code it can run, and misses dependences where it cannot, such as host code
that reads its input through C++ streams; it reports this. The cost is \numBenchHyTimeLo{} to
\numBenchHyTimeHi{} seconds per program (median \numBenchHyTimeMedian{}) for the hybrid interpreter under four
thread orders.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A CUDA program is a host program, running on the CPU, that issues work to the GPU. The work arrives at the GPU as
a sequence of \term{operations}: a \term{kernel launch} runs a function, the kernel, on many GPU threads at once,
a \term{copy} moves bytes between host memory and device memory or within device memory, and a \term{fill}
(\code{cudaMemset}) sets a range of device memory to one value. By default the GPU runs these operations one
after another, in the order the host issued them. That order is always safe, but it is often slower than
necessary, because two operations that touch different bytes could run at the same time, and an operation whose
inputs are ready could start before an unrelated operation finishes. CUDA lets a program express such freedom with
streams and with task graphs~\cite{cudaguide}, and research systems schedule GPU work from a dependence graph
between kernels or parts of kernels~\cite{Abdolrashidi2017Wireframe,Abdolrashidi2021BlockMaestro}. All of these
need to know which operations depend on which.

An operation \emph{depends} on an earlier one when they touch the same bytes and at least one of them writes them.
For regular code, where every address is a simple function of the thread index and the sizes, a compiler can work
out the bytes each kernel touches from the source code alone~\cite{Feautrier1991Dataflow}. For irregular code it
cannot. In a graph program the addresses a kernel touches are read from memory. For example, a breadth-first search
visits \code{cost[edges[i]]}, where \code{edges} holds the graph, and it runs that statement only for vertices whose
entry in a frontier array is set, an array that the previous kernel wrote. Which bytes the kernel touches is
therefore a function of the input graph and of everything the program computed before the launch. Graph
benchmark suites for GPUs consist mostly of such kernels~\cite{Che2013Pannotia,Burtscher2012Irregular,Wang2016Gunrock}.

A tool that schedules operations from predicted dependences pays differently for its two kinds of error. A
dependence it misses (a \term{false negative}) lets it run two operations in the wrong order, which must then be
detected and undone, an expensive rollback. A dependence it reports that does not occur (a \term{false positive})
only costs parallelism. The aim is therefore to miss none, and to report as few that do not occur as possible.

In this work we determine these dependences by running the program, with its input, in an interpreter that
records the bytes every operation touches. The first interpreter extends \memprint{}'s interpreter for C and C++
programs~\cite{memprintGeneralization}, which runs a program's syntax tree from \code{main()} and keeps the values
the program stores in memory, so that an address read from memory is known. The second runs the host code natively
and interprets only the kernels, which removes the limits of interpreting host code. We add the execution of
kernels, the bookkeeping that turns touched bytes into dependences, and the mechanisms that irregular GPU code
needs, and we measure the result against a GPU.

In this work, we make the following contributions:
\begin{itemize}
\item We describe a whole-program interpreter and a hybrid interpreter that run all threads of a kernel together as
arrays, and report for every pair of operations whether they depend on each other, through which buffer, over how
many bytes, and whether the dependence is certain or only possible (\secref{sec:interp}).
\item We show how to handle a kernel whose threads use different buffers chosen through pointers stored in
memory, by splitting the threads into groups by buffer (\secref{sec:split}), and a kernel whose touched bytes
depend on the order in which threads run, by running several legal thread orders and generalising what they could do
over any number of rounds (\secref{sec:schedules}).
\item We build an NVBit~\cite{Villa2019NVBit} tool that records the bytes each operation touches on a real GPU,
and a scoring method that compares two runs even when they issue a different number of operations
(\secref{sec:truth}).
\item We evaluate both interpreters on \numPrograms{} test programs and on \numBenchTotal{} unmodified benchmarks on
an NVIDIA A30. The hybrid interpreter misses no dependence and reports no wrong certain dependence on the
\numBenchHyDone{} benchmarks it completes (\secref{sec:eval}).
\end{itemize}

\section{Background and terms}
\label{sec:background}

This section defines the terms the rest of the paper uses. We assume only that the reader knows C.

\paragraph{Threads, blocks and kernels.} A kernel is a C++ function marked \code{\_\_global\_\_}. The host launches
it with a \term{grid} of $B$ \term{blocks}, each block a group of $T$ \term{threads}, and writes the launch as
\code{k<{}<{}<B,T>{}>{}>(\ldots)}. Every thread runs the whole function. A thread tells itself apart from the others through
the built-in values \code{blockIdx} and \code{threadIdx}, and usually computes from them the element it works on.
Threads of one block can share a small, fast memory (\code{\_\_shared\_\_} arrays) and wait for each other at a
barrier (\code{\_\_syncthreads()}). Threads of different blocks can communicate only through device memory, and
the order in which blocks run is not specified. An \term{atomic} operation, such as \code{atomicAdd(\&x, 1)},
reads and updates one memory location without another thread's update coming in between, and returns the old
value.

\paragraph{Operations and buffers.} We call every kernel launch, copy and fill an \term{operation}, and number
the operations in the order the host issues them. A \term{buffer} is one region of device memory obtained from
\code{cudaMalloc} or \code{cudaMallocManaged}. We measure memory in \term{units} of 4 bytes, so a dependence
through one \code{int} or \code{float} is one unit.

\paragraph{Dependences.} Operation $b$ depends on an earlier operation $a$ through a unit of a buffer if one of
three things holds. In a \term{read after write} (RAW), $a$ is the last operation before $b$ that wrote the unit,
and $b$ reads it, so $b$ needs the value $a$ produced. In a \term{write after write} (WAW), $b$ writes a unit that
$a$ was the last to write, so $b$ must not finish before $a$, or the final value would be $a$'s. In a \term{write
after read} (WAR), $b$ writes a unit that $a$ read after the last write, so $b$ must not overwrite it before $a$
has read it. We identify a dependence by its source operation, its destination operation, its kind and its buffer,
and we record over how many units it passes.

\paragraph{Certain and possible dependences.} A dependence is \term{certain} if the interpreter computed both accesses exactly,
and, when it ran the program under several thread orders (\secref{sec:schedules}), every order produced the
dependence. It is \term{possible} if at least one
of the two operations only perhaps touches it, for example because the access sits under a branch on a value the
interpreter does not know, or at an address it could not compute. A tool that consumes the dependences can rely on
a certain dependence, and must treat a possible one as present to stay safe.

\paragraph{Needed dependences.} If $c$ depends on $b$ and $b$ depends on $a$, then running the operations in an
order that respects the first two dependences also respects any dependence of $c$ on $a$. A scheduler therefore
needs only the dependences that are not implied by a path through others. In graph terms these form the
\term{transitive reduction} of the dependence graph, and we call them the \term{needed} dependences.

\paragraph{Indirect accesses and data-dependent branches.} An access is \term{indirect} if its address is computed
from a value loaded from memory, as in \code{a[b[i]]}. A branch is \term{data-dependent} if its condition reads
memory, as in \code{if (mask[tid])}. A dependence is \term{data-dependent} if it passes through units that were
touched by an indirect access or under a data-dependent branch. The interpreter marks these from the source code
(\secref{sec:events}). They are the dependences a compiler cannot determine, and the ones this paper is about.

\figref{fig:bfscode} shows both kinds in the kernel that expands the frontier in a breadth-first search, written
in the style of Rodinia's \code{bfs}~\cite{Che2009Rodinia}. Which threads pass the test on \code{mask[tid]},
which elements of \code{edges} they read, and which elements of \code{cost} and \code{updating} they write all
depend on the graph and on the previous levels of the search.

\begin{figure}[tbp]
\begin{lstlisting}
__global__ void expand(const Node *nodes, const int *edges, bool *mask, bool *updating,
                       const bool *visited, int *cost, int n) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    if (tid < n && mask[tid]) {                       // data-dependent branch
        mask[tid] = false;
        for (int i = nodes[tid].starting; i < nodes[tid].starting + nodes[tid].no_of_edges; i++) {
            int id = edges[i];                        // indirect: i comes from nodes[]
            if (!visited[id]) {                       // indirect, and a data-dependent branch
                cost[id] = cost[tid] + 1;             // indirect write
                updating[id] = true;
            }
        }
    }
}
\end{lstlisting}
\caption{The frontier expansion of a breadth-first search (\code{rodinia\_bfs}, one of our test programs). The
bytes the kernel reads and writes depend on the graph and on what earlier launches wrote.}
\label{fig:bfscode}
\end{figure}

\section{The interpreter}
\label{sec:interp}

\subsection{Overview}
\label{sec:overview}

Both interpreters take the program's CUDA source files and its command line, run the program on the CPU from
\code{main()}, and need no GPU. They differ in how they run the host code. \figref{fig:overview} shows the steps.
First, libclang~\cite{libclang} parses the source into a syntax tree. CUDA's own headers are replaced by a small
header of our own that declares the runtime functions (\code{cudaMalloc}, \code{cudaMemcpy} and so on). Second, the
program runs. The whole-program interpreter executes the host code's syntax tree as \memprint{}'s C++
interpreter does~\cite{memprintGeneralization} (\secref{sec:host}); the hybrid interpreter compiles the host code
and runs it natively (\secref{sec:hybrid}). In both, each call to a CUDA runtime function or kernel launch becomes
an operation, and every kernel is interpreted from its syntax tree (\secref{sec:kernels}). Third, each operation
records the units it read and wrote in each buffer. Fourth, the operations are folded, in order, into the
dependences between them. The program runs several times, under different thread orders, and the runs are merged
(\secref{sec:schedules}). The output is a list of operations, a list of dependences with their kinds, buffers, unit
counts and certainty, a template of the dependences of rounds whose number the thread order decides, and
optionally the address ranges each operation touched.

\subsection{Running the host program}
\label{sec:host}

The host part of a CUDA program is ordinary C++, and the interpreter runs it the way \memprint{}'s C++ interpreter
does~\cite{memprintGeneralization}. Every allocation, global variable and the stack is a memory \term{object}. A
pointer is a pair of an object and a byte offset into it. The interpreter keeps the integer value stored in every
4-byte unit of every object, and remembers which units hold pointers and to which object they point. As a result,
when the program reads a graph from a file into an array and later indexes another array with an element of it,
the interpreter knows the index. Floating-point values in memory are not kept, and a value the interpreter does
not know is marked unknown rather than guessed.

Device memory fits into the same scheme. Each \code{cudaMalloc} creates a new object of kind \emph{device}, and
each \code{\_\_device\_\_} or \code{\_\_constant\_\_} variable is an object as well. A \code{cudaMemcpy} copies the
stored values, and the pointer information, from one object to the other, so an index array built on the host and
copied to the GPU keeps its contents, and a table of device pointers built on the host still points to the right
buffers after the copy. A \code{cudaMemset} stores its value in the filled units.

A loop on the host that issues GPU work runs one iteration at a time, in program order. The interpreter otherwise
runs short counted loops as one step over all iterations (\secref{sec:kernels}), and we changed it so that an
allocation, copy or fill inside such a loop is carried out once per iteration, because each iteration creates a
different buffer or a different operation.

\subsection{Running the host program natively: the hybrid interpreter}
\label{sec:hybrid}

The whole-program interpreter must understand every line of the host code. Real host code reads its input with C++
streams and strings, uses library containers, or is written in old C dialects, and where the interpreter does not
model what the code does it computes a wrong execution: in our benchmarks, a graph read through
\code{std::ifstream} came out empty. The hybrid interpreter avoids interpreting the host code at all.

The program is compiled by \code{nvcc} as a shared library, with its \code{main()}, against a stand-in for the CUDA
runtime instead of CUDA's own. In the stand-in runtime, device memory is ordinary host memory: \code{cudaMalloc}
allocates zeroed host memory, a copy or fill is a \code{memcpy} or \code{memset}, and \code{\_\_device\_\_} and
\code{\_\_constant\_\_} variables live in the host copy that \code{nvcc} creates for each of them. The interpreter loads
the library into its own process and calls the program's \code{main()}, so the host code runs at native speed with
every library it uses. Every allocation, copy, fill and launch calls back into the interpreter. At a launch, the
interpreter binds the kernel's arguments from the launch's argument array (a pointer argument becomes the buffer it
points into, a structure passed by value is copied field by field) and runs the kernel as in \secref{sec:kernels}.
The kernel's loads read the program's real bytes, with the signedness of their C type, and its stores write them, so
the host code continues from the kernel's results. Every value is concrete, so the hybrid interpreter knows values
that the whole-program interpreter does not, such as those of \code{drand48}.

Two pieces of information that the whole-program interpreter takes from the host code are recovered differently.
Whether an operation was issued under data control (\secref{sec:events}) is decided from the source for each call
site; the stand-in runtime records the return address of every copy and fill, and \code{addr2line} maps it to its
line. The host side of a copy, which the whole-program interpreter tracks as an object, is tracked as a region of
host memory named in order of first use; locals on the stack are left out, as the whole-program interpreter keeps
scalar locals out of memory. Because the program's native state cannot be reset, each thread order runs in a
process of its own, and the processes' results are merged.

\subsection{Running a kernel: all threads at once}
\label{sec:kernels}

A kernel launch runs the kernel's body once, for all of its threads together. Every variable of the kernel holds
an array with one value per thread, and every statement is carried out for all threads before the next statement
starts. \memprint{}'s interpreter uses the same representation to run all iterations of a loop at once, and for a
kernel the threads take the place of the iterations. The thread's \code{threadIdx.x} is an array $0, 1, 2,
\ldots$; an expression such as \code{blockIdx.x * blockDim.x + threadIdx.x} is computed for all threads with one
array operation; and \code{edges[i]}, where \code{i} differs per thread, loads one element per thread from the
stored values of the object \code{edges} points to.

A branch splits the threads. The interpreter evaluates the condition for every thread, runs the branch only for
the threads where it holds, and merges the variables of the two groups afterwards. A loop whose trip count differs
per thread runs until no thread continues, and a thread that returns from the kernel stops taking part. In this
way every thread follows its own control path, decided by the values it loaded.

We call this order of execution \term{lockstep}: statement by statement, all threads at a time. Lockstep is one
order in which the GPU could legally run the threads of a kernel that has no data races, because the GPU guarantees
nothing about the relative progress of threads between barriers. A barrier, \code{\_\_syncthreads()}, has no work
to do in lockstep, since every thread has already reached it when the statement before it finishes. Each block has
its own copy of the kernel's \code{\_\_shared\_\_} arrays. Atomic operations to the same address from different
threads take effect one after another in thread order, and each thread receives the value that was there before
its own update, as on the GPU. The interpreter runs the blocks of a large grid in groups of at most $2^{18}$ threads
to bound its memory use.

\subsection{Recording what each operation touches}
\label{sec:events}

Every operation records, per object and per byte, whether it read the byte and whether it wrote it. A kernel
records every load and store that its threads carry out, a copy records the bytes it reads at the source and writes
at the destination, and a fill records the bytes it writes. A read of a byte that the operation has already written
for certain is not recorded as a read, because it reads the operation's own value, not an earlier operation's: in
\code{tmp[i] = 0; tmp[i] += a[i][j] * x[j];} the kernel does not depend on whoever wrote \code{tmp} before it. The
interpreter also records the host code between two operations as an operation of its own, which a tool can ignore;
the evaluation leaves it out.

A record has two further marks. The first says whether the access is only possible, which is the case when the
interpreter could not compute the access exactly. An address it could not compute covers the whole object it
points into, and an access under a branch whose condition is unknown is recorded but marked as possible. An access
through a pointer whose object is unknown is recorded as a possible access to every device buffer, and so is an
access past the end (or before the start) of a device buffer. On the GPU such an access reaches whatever memory lies
there, often the next buffer, which the interpreter cannot know; it reports where the access happens, because it is
usually a bug in the program. The second mark says whether the access is data-dependent (\secref{sec:background}).
The interpreter decides this from the source code before the program runs, by marking every value that is loaded
from memory, or computed from such a value, or assigned under a condition that is, and repeating until nothing
changes. An access whose address or whose enclosing conditions use a marked value is data-dependent, and so is every
access of an operation that the host issued from a loop whose condition depends on device data, such as a loop that
runs until the GPU reports that nothing changed.

\subsection{From touched bytes to dependences}
\label{sec:deps}

The operations are folded into dependences in the order they were issued. For every unit of every object the
interpreter keeps the last operation that certainly wrote it, the operations that possibly wrote it since then,
and the operations that read it since then. When the next operation arrives, every unit it reads produces a RAW
dependence on the last writer and on each possible writer since, every unit it writes produces a WAW dependence on
them and a WAR dependence on each reader, and then the operation's own writes replace the history of those units. A
dependence is certain if both of its accesses are certain and no operation possibly wrote the unit in between, and
possible otherwise. The counts of units are summed per dependence. \figref{fig:example} shows the result for a short
program.

\subsection{Threads that use different buffers}
\label{sec:split}

Some kernels choose a buffer, not only an element, from data. \figref{fig:ptrsel} shows a kernel that distributes
elements into one of four buckets, each a separate buffer, through a table of device pointers that the host
copied to the GPU. In lockstep, the statement \code{bucket[k][\ldots] = i} loads one pointer per thread, and the
pointers of different threads point to different buffers. The interpreter's pointer is a pair of one object and
an offset, so it cannot represent ``buffer 0 for these threads and buffer 3 for those''. Before the change
described here, such a pointer became unknown, every write through it became a possible write to every device
buffer, and every dependence from the kernel to the four consumers was only possible.

\begin{figure}[tbp]
\begin{lstlisting}
__global__ void distribute(const int *keys, int *const *bucket, int *count, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;
    int k = keys[i] % 4;
    bucket[k][atomicAdd(&count[k], 1)] = i;   // the buffer itself is chosen by keys[i]
}
\end{lstlisting}
\caption{A kernel that writes each element into one of four buffers, through a table of pointers in device memory
(\code{ptrsel}). The four consumer kernels each read one buffer.}
\label{fig:ptrsel}
\end{figure}

We resolve this by splitting the threads. When a kernel loads pointers from memory and the threads' pointers name
different objects, the interpreter groups the threads by the object their pointer names, and then runs the
statement, and the rest of the enclosing block of code, once for each group, with only that group's threads
active. Inside a group the pointer names one object, so every access through it is exact. After the last group,
the variables of all groups are merged as after a branch. A pointer variable that ends up naming different objects
in different groups becomes unknown at the merge, which is safe.

Running a statement a second time is correct only if its first, interrupted execution changed nothing. The
interpreter therefore counts stores and atomic operations, notes the count when each statement starts, and splits
only if the count is unchanged when the pointer is loaded. If a store already happened, the pointer stays unknown
as before. For \code{bucket[k][atomicAdd(\ldots)]} the split happens, because C++17 evaluates the array expression
\code{bucket[k]} before the index, so the pointer is loaded before the atomic operation~\cite{cppstd17}. A pointer
loaded after an atomic operation in the same statement cannot be split. The interpreter also limits the split to
at most 64 different objects.

\subsection{Kernels whose result depends on thread order}
\label{sec:schedules}

Lockstep is a legal order of execution, but it is not the only one, and for some kernels the bytes touched depend
on the order. The connected-components kernel in \figref{fig:cc} lowers labels in place. Thread $e$ reads the
labels of the two ends of edge $e$ and writes the smaller into the larger with \code{atomicMin}. If another thread
lowered one of those labels earlier in the same launch, thread $e$ reads the new value, otherwise the old one, so
which threads write, and which units, depends on the order. The host repeats the kernel until a launch changes
nothing, so the number of launches depends on the order too. On the GPU, \numCcGpuRuns{} runs of this program took
\numCcGpuRoundsLo{} to \numCcGpuRoundsHi{} rounds, and each of \numCcReps{} traced runs touched different bytes. In
lockstep, every thread reads its labels before any thread of the launch writes one, so no update reaches another
thread within the same round, and the program takes 24 rounds. With lockstep alone, the interpreter reported all of
its dependences as certain, and \numCcLockFalseLo{} to \numCcLockFalseHi{} of them did not occur in a given GPU run
(\secref{sec:eval-cc}).

\begin{figure}[tbp]
\begin{lstlisting}
__global__ void hook(const int *src, const int *dst, int *label, int *changed, int m) {
    int e = blockIdx.x * blockDim.x + threadIdx.x;
    if (e >= m) return;
    int a = label[src[e]], b = label[dst[e]];   // may see another thread's update, or not
    if (a < b && atomicMin(&label[dst[e]], a) > a) *changed = 1;
    if (b < a && atomicMin(&label[src[e]], b) > b) *changed = 1;
}
\end{lstlisting}
\caption{One round of connected components by label propagation (\code{cc}). The host launches it until
\code{changed} stays zero.}
\label{fig:cc}
\end{figure}

\paragraph{Several legal orders.} The interpreter runs the whole program under four thread orders. The first is
lockstep. In the other three, each block runs to completion before the next starts, in the order of block numbers,
in reverse order, or in a random order, and within a block the warps of 32 threads run one after another in the
same order, unless the kernel uses \code{\_\_syncthreads} or shared memory, which require the warps of a block to
run together. A later block or warp then sees what earlier ones wrote. Only some kernels need these orders. A launch
in which no unit is both read and written (by any thread, an atomic counting as both) computes the same result in
any order, so the lockstep run notes which kernels had a launch that read and wrote one unit, and the other orders
reorder only those and run the rest in lockstep.

\paragraph{Merging the runs.} We match the operations of the runs by their common beginning and their common end,
because a loop that runs a different number of rounds adds or removes operations in the middle of the sequence. A
dependence stays certain only if every run has it between operations that every run has, every run reports it as
certain, and it does not lead from before the point where the runs part to after the rounds that differ, since
those rounds decide which operation last wrote each unit. All other dependences of the first run, and those that
only other runs have, become possible and are marked as depending on the schedule.

\paragraph{What other orders could do.} Four orders are a sample. A GPU run can interleave threads differently and
produce a dependence none of the four produced, and a tool that relies on the result must not miss it. The
interpreter therefore over-approximates where the orders disagree. Each run keeps, per operation and buffer, the
units read and written. For an operation that every run issues but that touched different units in different
runs, the interpreter takes the union over the runs, and adds a possible dependence between it and every other
operation whose union conflicts with it (one writes a unit the other reads or writes). Where the runs issue
different numbers of operations, the interpreter finds the shortest repeating sequence of operations that covers
the part where they differ, such as \emph{fill the flag, launch the kernel, copy the flag back}, and writes a
\term{round template}. For each position in a round it takes the union of the units touched over every round of
every run, and it records every conflict as a possible dependence: between two positions in one round, from a round
to any later round, from an operation before the loop to every round, from every round to an operation after the
loop, and between the operations before and after the loop. A tool instantiates the template for the number of rounds
the program actually runs; the scorer does so for the traced run. This over-approximation removes missed dependences
at the cost of reporting dependences that a given run does not have.

\paragraph{Writes that every order makes.} Much of that cost is avoidable. In GraphBIG's connected components,
one kernel copies every label from a second array into the first in every round, at the index of the thread, under
the condition that the thread number is below the number of vertices. Whatever order the threads run in, this
kernel overwrites every label, so no dependence through a label can reach from one round past it into a later
round. The interpreter marks such writes: a write is made in every order if it is certain, if neither its address
nor any condition it runs under (including an earlier \code{return}, \code{break} or \code{continue} under a
condition) uses a value loaded from memory, and if the launch's grid and block sizes do not either. Copies and fills
that the host issues are made in every order as well. For each position in a round, the interpreter keeps the units
that every round of every run wrote in this way, and a template dependence through a unit that some operation
between its two ends writes in this way is dropped; such a unit's dependence is on that operation instead. Where
only the operations between two consecutive rounds are in the way, the dependence is kept for the next round only.
The same rule applies to the union of an operation that every run issues but that touched different units in
different runs: no dependence is added through a unit that an operation between the two, in every run, wrote in
this way.
Conversely, a dependence of an operation in the rounds through a buffer whose units that position touched
differently in different rounds or runs is reported as possible, not certain, even when every run had it: another
order could touch other units.

\subsection{What the interpreters cannot know}
\label{sec:unknown}

Both interpreters need the program's input, because the bytes an irregular kernel touches are a function of it. In
a kernel they do not model floating-point values stored in memory or a pointer loaded in a statement after a store,
and accesses that depend on such values are recorded as possible. The whole-program interpreter also does not model
every library function the host code calls (for example \code{drand48}, C++ file streams and strings); the
\code{maybe} test program checks the first case. When the host code calls such functions, the values the program
computes from them are unknown or wrong, and the operations it issues may be too. The interpreter counts these calls
and its parse errors and warns that the result is unreliable, but it cannot recover the operations it did not see;
the hybrid interpreter, which runs the host code natively, is the remedy. A kernel whose result depends on thread
order is handled by sampling orders and over-approximating what other orders could do (\secref{sec:schedules}).

\section{Measuring the truth on a GPU}
\label{sec:truth}

To measure the interpreter's accuracy, we need the bytes each operation actually touches on a GPU. We built an
NVBit~\cite{Villa2019NVBit} tool for this. NVBit is a framework that inserts code before chosen machine
instructions of a kernel when the kernel is loaded. Our tool inserts, before every load, store and atomic
operation on global memory, a call that sends the addresses of the 32 threads of the warp, the access size and
whether it reads or writes, together with the number of the current launch, to a buffer that a CPU thread empties.
On the host side the tool intercepts the CUDA driver's functions for allocation, copies, fills and kernel launches,
so it knows every buffer's base address and size and every operation's position. It writes, per operation and
buffer, the ranges of units read and written, in the same format the interpreter can write.

The tool was written against NVBit 1.7 on a machine without a GPU, and it needed three changes to work with NVBit
1.8 and CUDA 13.4. First, the GPU side of the buffer must be flushed explicitly after each launch and at the end,
with a small kernel loaded as a separate module, otherwise the last partly filled buffer, which for a small program
holds all records, is lost. Second, the launch number must be set before the instrumented code is enabled for the
launch, otherwise the records carry a wrong number. Third, the CUDA 13 runtime may launch kernels through
\code{cuLaunchKernelEx}, which the tool must intercept as well. In addition, the interpreter's stand-in CUDA header had to declare the launch function
that clang uses when it finds a recent CUDA installation on the machine.

\paragraph{Comparing two runs.} The traced run's bytes are folded into dependences by the same code as the
interpreter's, so the two sides differ only in which bytes each operation touched. Buffers are matched by the
order of their allocation, and operations by their order. When the two runs issue different numbers of operations,
as \code{cc} does, operations are matched by common beginning and common end as in \secref{sec:schedules}, the
interpreter's round template is instantiated for the traced run's rounds and added as possible dependences, and a
traced dependence through an operation that remains unmatched counts as missed. A dependence is identified by its
source and destination operation, its kind and its buffer. Comparing the interpreter's dependences with the traced
run's gives five counts: certain dependences the run has (true positives) and does not have (false positives),
possible dependences the run has and does not have, and the run's dependences the interpreter does not report at
all (false negatives). From them we compute three scores. \term{Certain precision} is the share of the
interpreter's certain dependences that the traced run has. \term{Recall} is the share of the traced run's
dependences that the interpreter reports, certain or possible. \term{Certain recall} is the share it reports as
certain. \term{Units error} is, over the dependences both have, the summed difference in unit counts divided by
the traced units. Dependences through memory that is not a \code{cudaMalloc} buffer (\code{\_\_device\_\_} variables, host
memory) are not scored, since the tool does not see them as buffers. We also compute the scores over the needed
dependences of each side.

\subsection{Before the input is known}
\label{sec:eval-input}

The interpreter needs the input. To see what depends on the input and what does not, we ran \code{rodinia\_bfs}
on three random graphs (\tabref{tab:patterns}). The searches took 51 to 63 operations and produced 417 to 656
dependences, and only 48 dependences have the same operations and units in all three graphs, most of them
through the one-unit flag that the host copies back after every round. The
exact bytes are therefore a property of the input. We then describe each dependence by a \term{pattern}: the names
of its two operations, its kind, its buffer, and how many operations apart they are, for example ``\code{expand}
then \code{commit} one operation later, RAW through \code{updating}''. All 24 patterns of the needed dependences are
the same for the three graphs. The structure of the dependences is therefore a property of the program, and only
the number of rounds and the units are a property of the input. A tool that must decide before the input is known
could use the patterns, and refine them with the interpreter once the input is available. We have not built such
a tool. Run without the input, the interpreter today stops after one round of the search, because the loop's exit
condition comes from the GPU and is unknown, and it reports \numNoInputPatterns{} of the \numNoInputPatternsOf{}
patterns that connect operations at most six apart, nearly all of them as possible.

\section{Related work}
\label{sec:related}

\paragraph{Static analysis of GPU kernels.} Compilers determine the dependences of loops and kernels whose
addresses are affine functions of loop indices with the polyhedral model~\cite{Feautrier1991Dataflow,grosser2012polly},
but an address read from memory falls outside that model. GPUVerify~\cite{Betts2012GPUVerify} proves that a kernel
is free of data races for all inputs, and GKLEE~\cite{Li2012GKLEE} explores a kernel's behaviour with symbolic
inputs. Both reason about one kernel and treat memory contents as arbitrary, so neither tells which bytes a kernel
touches on a given input, and neither relates one launch to the next. Our interpreters answer the latter question,
for one input.

\paragraph{Dynamic analysis and emulation.} NVBit~\cite{Villa2019NVBit} and race detectors such as
BARRACUDA~\cite{Eizenberg2017Barracuda} observe the accesses of a running program on the GPU, as our ground-truth
tool does. They give the exact bytes of one run, but only by running the program on the GPU with instrumentation,
and only after the fact. GPU emulators and simulators such as Ocelot~\cite{Diamos2010Ocelot} and
GPGPU-Sim~\cite{Bakhoda2009GPGPUSim} run compiled kernels on the CPU, one thread or warp after another, and could
record the same bytes for one order of execution. Our interpreters run kernels from source with all threads as
arrays, report which dependences are certain and which only possible, and cover other orders than the one they
ran.

\paragraph{Inspector and executor.} Runtime parallelisation of irregular loops runs an \term{inspector} that reads
the index arrays to compute the loop's dependences, and then an \term{executor} that runs the loop in an order that
respects them~\cite{Saltz1991Inspector}. The interpreters are inspectors for a whole CUDA program. For accesses
whose indices come only from the input, an inspector can be cheap, but in the breadth-first searches the indices
depend on values earlier kernels computed, so finding the dependences means computing those values, which the
interpreters do.

\paragraph{Dependence-driven GPU scheduling.} Wireframe~\cite{Abdolrashidi2017Wireframe} and
BlockMaestro~\cite{Abdolrashidi2021BlockMaestro} run GPU work from a dependence graph between thread blocks of
consecutive kernels, and CUDA graphs~\cite{cudaguide} let the programmer state dependences between operations.
They need the dependences as input. BlockMaestro derives them from the kernels' memory accesses when these are
regular; the interpreters could supply them for irregular kernels when the input is known.

\section{Limitations}
\label{sec:limits}

A limitation of the interpreters is that they need the program's input, which means that their results are for
that input only (\secref{sec:eval-input}). A tool that schedules from them must run them on the input it will use.

A limitation of the whole-program interpreter is that it must understand all of the host code, which means that
programs whose host code uses C++ streams, option parsers or old C dialects come out with operations missing
(\secref{sec:eval-bench}). It warns when this happens; the hybrid interpreter does not have this limitation.

A limitation of the over-approximation for thread order is that it reports every dependence another order could
produce, which means that kernels whose result depends on thread order come out with many possible dependences that a
given run does not have (\numBenchHyPossNo{} over the benchmarks). It also rests on the units the sampled orders
touched: a GPU run that touched a unit none of the four orders touched could still produce a dependence that is not
reported, although none of our traced runs did.

A limitation of splitting threads is that it applies only to a pointer loaded before any store in its statement,
which means that a pointer loaded after an atomic operation in the same statement still makes every access through
it a possible access to every buffer.

A limitation of the cost is that the interpreters simulate every GPU thread on one CPU core in Python, which means
that their run time grows with the number of threads, and that GraphBIG's \code{betweenness}, ten times larger than
any other benchmark, did not finish in two hours. The whole-program interpreter's run time also grows with
sequential host loops, and the extra thread orders
multiply the cost of either interpreter by up to \numHyOrdersHi{} for programs whose reordered kernels have many
warps (\secref{sec:eval-overhead}).

A limitation of the evaluation is that every program was traced once on one GPU, with inputs small enough for the
tracer, which means that the scores are for those runs and inputs.

\section{Conclusion}
\label{sec:conclusion}

We showed that the memory dependences between the operations of a CUDA program, including those that pass through
bytes chosen by data, can be found before the program runs on the GPU, by running its kernels in an interpreter on
the CPU with its input. Running all threads of a kernel at once as arrays keeps the cost proportional to the work of
the kernels, splitting threads by the buffer their pointers name makes accesses through pointer tables exact, and
running several legal thread orders, with an over-approximation of what other orders could do, keeps every
dependence a GPU run has among the reported ones. Running the host code natively removes the need to understand
it. On \numBenchHyDone{} unmodified benchmarks, the hybrid interpreter missed no dependence and reported no wrong
certain dependence. The next steps are to reduce the possible dependences reported for kernels whose result depends
on thread order, and to reduce the cost for programs with very many launches.
